# Avalonia Windows client product contract

## Режимы клиента

- До авторизации Avalonia-клиент показывает полноэкранный заблокированный access-gate с
  номером места, входом и регистрацией.
- При запуске access-gate должен быть виден уже в первом отрисованном кадре;
  промежуточный белый или пустой экран недопустим. До авторизации используется
  тёмная палитра клиента даже при светлой системной теме Windows.
- После входа пользователь получает обычный Windows-рабочий стол: приложение не
  заменяет Windows собственным shell.
- После входа Avalonia-клиент сворачивается в небольшой borderless-виджет без системных
  кнопок окна. Крестик сворачивает его в HUD-таймер, а не закрывает клиент.
- После входа виджет располагается у правого края рабочего стола. Аватар обозначает профиль; виджет показывает ник, телефон, баланс, доступное время,
  оставшееся время активной сессии и явную кнопку выхода.
- Интерфейс Win-клиента использует согласованную тёмную палитру: графитовый
  фон и карточки, светлый текст и lime-зелёный акцент. Системная светлая тема
  Windows не должна переключать клиент в белую палитру.
  Avalonia использует `RequestedThemeVariant="Dark"`: поля ввода, в том числе
  пароля, сохраняют тёмный фон и светлый текст при фокусе и наведении.
- При публикации Windows-клиент называется `HubShell.exe`. Тот же знак
  используется для файла, главного окна и окна истории; установка, автозапуск,
  восстановление после сбоя, киоск и диагностика обращаются к этому имени.
- Значок в системном трее извлекается из запущенного `HubShell.exe`, а его
  подпись — `HubShell`; системный стандартный значок приложения не используется
  как основной вариант.
- Виджет после входа оформлен по `ref/Панель HUBSHELL на рабочем столе Windows 11.png`:
  профиль, соединение, баланс, активная сессия, тарифы и пакеты; перенос и
  история расположены рядом внизу. Ширина — 390 DIP, высота — до 1000 DIP,
  с ограничением рабочей областью экрана и вертикальной прокруткой.
  Крестик гостя и пользователя сворачивает окно в вертикальную HUD-кнопку
  68×280 DIP вплотную к правой границе рабочей области экрана. Кнопка показывает
  суммарный известный остаток сессии в формате ЧЧ:ММ (без сессии — `--:--`);
  клик разворачивает виджет. Переход занимает 260 мс, с изменением размеров,
  положения и плавным затуханием. Клиент и сессия продолжают работать.
  Блокировка немедленно отменяет переход и возвращает access-gate.
  Maintenance отменяет переход и открывает обычное окно обслуживания без Topmost.
  «Выйти» завершает сессию с подтверждением; отдельный Windows tray сохранён.
  Данные, статусы пакетов и доступность действий сохраняют существующий контракт.
- Гостевой V2-виджет оформлен по `ref/Синеокий рабочий стол с панелью HUBSHELL.png`.
  Он использует общую оболочку с профилем «Гость», соединением, активной сессией
  и оплаченными пакетами из гостевого ledger. Баланс, телефон, каталог, история,
  ручная активация пакета и личная бронь аккаунта гостю не показываются.
  Для гостя высота окна — до 700 DIP, с ограничением рабочей областью экрана.
  Список обновляется после допродажи и расхода времени; terminal-пакеты скрыты.
  Остаток показывается в минутах: ledger не хранит исходную длительность каждого
  отдельного guest grant. Кнопка переноса из референса пока отключена: V2 guest
  transfer не реализован. Выход использует подтверждение и `StopGuestAccess`.
- История аккаунта и уведомления виджета используют тёмно-бирюзовую палитру
  виджета. История имеет высоту по содержимому и прокрутку длинных списков.
  Подтверждения покупки, переноса и завершения сессии компактны, сохраняют
  предупреждения и оба действия; Escape отменяет, начальный фокус — на отмене.
- В виджете есть каталог опубликованных тарифов. Покупка требует явного
  подтверждения и списывает деньги только через backend; сохранённый пакет
  можно отдельно активировать.
- В каталоге Win-клиента показываются только опубликованные активные тарифы,
  совместимые с зоной текущего workstation и аудиторией текущего покупателя;
  общий тариф без зоны совместим со всеми зонами. Для зарегистрированного
  клиента допустимы `all` и `registered`, для гостевой продажи — `all` и
  `guest`. Backend остаётся источником решения.
- Оплата оператора выполняется в web-оболочке. Смешанная оплата в MVP — это
  наличные плюс перевод; банковские карты не поддерживаются.
- Временной тариф содержит отдельные серверные окна продажи и расходования.
  Вне окна продажи он не попадает в каталог и не покупается; купленный пакет
  вне окна расходования не теряет минуты. Avalonia отображает каталог и
  уведомления из server snapshot и не определяет доступность по локальным
  часам. Если уже активный пакет достигает закрытия окна, backend завершает
  сессию и сжигает остаток пакета; клиент получает это только из нового
  server snapshot.
- В активной гостевой сессии виджет показывает название оплаченного тарифа,
  количество блоков и оставшееся время из server snapshot. Для поминутного
  режима показывает оставшееся время по балансу и прошедшие минуты/метры из
  server snapshot; заглушка вместо времени допустима только если backend
  действительно не прислал ни тариф, ни meter, ни остаток по балансу.
- Поле «Остаток по балансу» приходит готовым из server snapshot и означает
  только число минут по действующей поминутной ставке зоны. Win-клиент не
  пересчитывает его через цену или длительность пакетных тарифов.
- Главный таймер активной сессии показывает единый прогноз до принудительного
  выхода: оставшиеся минуты активного и доступных к моменту перехода queued
  пакетов, затем server-provided минуты поминутного баланса. Закрытый ночной
  пакет не добавляется; закрытие окна активного ночного пакета обрывает прогноз
  и сжигает его остаток. Это только отображение snapshot, а не локальное
  решение о списании или доступности.
- Во время активного пакета поле времени, рассчитанного по балансу, скрывается;
  оно появляется только после перехода на поминутный источник. Завершённые
  `exhausted` и `burned` пакеты в пользовательском списке не показываются.
  Видимые состояния пакета — только `Активный` и `В очереди` с названием
  тарифа, понятным остатком и длительностью.
- Отображаемый таймер считается локально от последнего подтверждённого
  server snapshot и монотонно уменьшается в рамках одного источника времени.
  Heartbeat/polling корректирует drift, но не заменяет каждую секунду скачком;
  финансовым источником истины остаётся backend. Переход package → следующий
  package → per-minute принимается только из server result.
- Повторный снимок с тем же источником и тем же остатком не перезапускает
  локальный отсчёт. Меньший остаток от сервера применяется сразу; увеличить
  отображаемое время может только подтверждённый новый пакет, смена источника
  или пополнение баланса в поминутном режиме.
- У пакета нет отдельной пользовательской кнопки «Завершить»: завершение
  игровой сессии выполняется только общей кнопкой «Выйти».
- После входа каждая пользовательская кнопка «Выйти» сначала открывает понятное
  подтверждение. При отмене клиент не отправляет запрос на остановку; при
  подтверждении предупреждает о сгорании остатка текущего начатого пакета и
  только затем запускает существующее server-backed завершение сессии.
- Перенос сессии — вторичный сценарий и находится в сворачиваемом блоке, а не
  занимает основной экран.
- История аккаунта открывается в отдельном fixed-size borderless-окне в той же
  тёмной палитре. Она не изменяет размер основного виджета, показывает
  server-backed строки с локальным форматом времени `dd.MM.yyyy HH:mm` и
  всегда имеет явную кнопку закрытия.
- Выбор темы пользователем в виджете не показывается: тему назначает клуб и
  передаёт через workstation heartbeat.
- Название станции в access-gate и виджете приходит из server-backed
  `workstation.name` того же authenticated heartbeat. Технические
  `workstation_id` и device ID не выводятся пользователю; до получения имени
  показывается нейтральное «Игровое место».
- Регистрация и вход используют пароль, не PIN. Телефон вводится в устойчивой
  маске `+7 (9__) ___-__-__` и отправляется backend в canonical-виде.
- Успешные вход и регистрация на назначенном ПК создают одну server-backed
  активную сессию этого клиента на текущем месте. До ответа `SessionSnapshot`
  пользовательский виджет не считается запущенным.
- Если приложение/ПК перезапустились или связь временно пропала во время
  active session, authenticated heartbeat обнаруживает её снова, а Win-клиент
  восстанавливает portal/session state без повторного пароля. Resume разрешён
  только для сессии этого workstation; явный выход сначала завершает сессию.
- Выход выполняется по состояниям: запрос stop, подтверждение backend,
  очистка доступа и открытие access-gate, затем allowlisted restart. До
  подтверждения backend клиент не показывает успешное завершение и не
  запускает перезапуск; ошибка каждого этапа остаётся видимой и допускает
  безопасный повтор. Произвольные shell-команды запрещены.
- В пользовательском access-gate доступны только вход и создание аккаунта;
  ручная проверка подключения и вход менеджера не показываются. Состояние
  соединения обновляется автоматически.
- До пользовательского входа access-gate работает в `Locked`, всегда остаётся
  `Topmost`, а `Alt+Tab`, `Win+R` и `Win+D` подавляются в локальном обработчике и должны
  быть подтверждены Windows policy/native smoke. Запрет произвольного запуска
  приложений пока не является частью базового lock.
- Режим обслуживания не имеет публичной кнопки в пользовательском access-gate
  и не запускает клиентскую сессию. Его отдельный контролируемый route описан
  ниже и реализован в клиенте.
- Скрытый менеджерский route допускается по `Ctrl+Alt+P` только когда
  заблокированное окно клиента имеет фокус. Комбинация открывает форму пароля,
  но сама по себе не даёт доступ; пароль проверяется отдельным PBKDF2-verifier.
  По явному решению пользователя 2026-10-11 разрешён глобальный keyboard hook
  исключительно в Locked access-gate; в User/Maintenance он снимается. `BlockInput`
  не используется. Клавиши Win подавляются вместе с Win+D/Win+R, чтобы отпускание
  заблокированной комбинации не открывало Start; обычный ввод и Ctrl+Alt+P доступны.
- `Ctrl+Alt+Del` не перехватывается: Task Manager может быть запущен для smoke,
  но access-gate должен оставаться поверх обычного окна; это не заменяет
  Windows security boundary.
- В профиле `app_gate` после успешной проверки менеджер может скрыть application
  shell в трей и увидеть обычный Windows Desktop. Это не отключает Explorer,
  Start Menu, Alt+Tab или другие политики Windows. В production `shell_launcher`
  клиент остаётся shell-процессом, поэтому полноценное обслуживание Desktop
  выполняется отдельной maintenance/admin учётной записью. Любое временное
  изменение Windows policy, если оно будет утверждено отдельно, выполняется
  только явным обратимым platform-policy действием с audit и native Windows
  verification.

## Постоянный виджет и восстановление процесса

- В пользовательском режиме виджет всегда показан под обычными окнами
  (HWND_BOTTOM), без Topmost и без захвата фокуса. Переключение приложений
  не скрывает его. После Win+D адаптер восстанавливает native visibility
  каждые 250 мс только в User-режиме, сохраняя HUD/развёрнутое состояние.
  Maintenance не восстанавливается этой проверкой. Win+D, игры и DPI требуют
  отдельной native-проверки.
- Обычное закрытие, в том числе Alt+F4, отменяется. Завершение Windows разрешено.
  В меню трея нет команды выхода. Менеджер после существующей проверки пароля
  получает окно без Topmost и может скрыть его через предусмотренную кнопку.
- Опциональная служба `HubShell.Watchdog` (LocalSystem) проверяет существующую
  локальную console-сессию каждые 2 секунды и восстанавливает отсутствующий клиент
  под её пользователем, с пользовательским окружением. Создания/смены учётных
  записей, kiosk policy, keyboard filter и смены shell нет.
- Служба запускается тем же `HubShell.exe --watchdog-service`; UI и service различаются
  режимом запуска. Session-local mutex предотвращает второй UI-процесс.
  Повторные попытки после запуска/ошибки ограничены задержкой 10 секунд;
  ошибки восстановления записываются в Windows Application Event Log.
- Установка службы требует администратора и каталога Program Files либо `C:\GameClub`
  с ACL: SYSTEM/Administrators — FullControl, Users — ReadAndExecute: запуск SYSTEM
  из пользовательского LocalAppData недопустим. `-RegisterWatchdogService` заменяет
  HKCU Run/recovery task для этой установки; SCM настроен на перезапуск службы.
  Пользователь Windows и его политики не меняются. Native SCM/WTS не проверены на Linux.
- Глобальный WH_KEYBOARD_LL устанавливается только для Locked, снимается при User,
  Maintenance и Dispose. Состояние клавиш не сохраняется и не логируется. Отказ
  установки записывается в startup diagnostics. Hook остаётся ограничением приложения,
  не системной границей защиты; Ctrl+Alt+Del не перехватывается.

## Авторизация и регистрация

- Вход: `ник + пароль` или `телефон + пароль`.
- После операторского сброса аккаунт допускает вход с пустым паролем. Сразу
  после входа Avalonia-клиент показывает обязательную форму нового пароля с повтором;
  доступ к балансу, тарифам и сессии открывается только после совпадения полей
  и подтверждения backend.
- Регистрация: ник, телефон, пароль. После неё можно завершить flow и пополнить
  депозит у оператора либо сразу войти и получить бесплатные минуты по серверной настройке
  `GAMECLUB_LOGIN_GRANT_MINUTES` (по умолчанию 1; 0 отключает период).
- При активной сессии на другом месте обычный второй вход не создаёт сессию;
  клиенту предлагается подтверждённый перенос. После подтверждения на старом
  ПК новый ПК принимает тот же аккаунт обычным входом без ID/кода; старый ПК
  сначала очищает portal/access-gate state и только затем выполняет restart.

## Тарифы и уведомления

- При новом входе показать совместимый сохранённый пакет и предложить его
  активировать. Несовместимый пакет другой зоны показать с понятной причиной,
  не расходуя его.
- Новый тариф, купленный в активной сессии при пустой очереди, стартует сразу.
  После завершения пакета следующий совместимый пакет запускается автоматически.
  Если первый пакет в очереди пока нельзя расходовать, клиент запрашивает у
  backend активацию подходящего следующего пакета; решение не принимается по
  локальным часам.
- Если покупка тарифа отклонена из-за недостаточного баланса, клиент показывает
  явное уведомление «Недостаточно средств на балансе» в виджете; ошибка не может
  завершаться без видимой обратной связи.
- При автоматическом старте показать краткое уведомление: активированный тариф
  и остаток пакетов. Оно закрывается само через 3 секунды и имеет собственную
  кнопку закрытия.
- При исчерпании всех пакетов и баланса завершить сессию и перезапустить ПК.
- Пороговые уведомления приходят из server-backed notification rules. Клиент
  получает `time_notifications` в session snapshot через gRPC, дедуплицирует
  событие по его идентификатору, воспроизводит стандартный звук или разрешённый
  wav/mp3 через Windows adapter и показывает tray balloon как Windows notification.
  Offline/reconnect не должны повторять уже подтверждённое событие; Linux host
  использует no-op platform presenter и видимый portable banner.
- При нулевом или отрицательном балансе Win-клиент показывает `0 минут` и не
  рассчитывает кредитное время. Решение о продолжении поминутной сессии и её
  остановке принимает backend по группе клиента и лимиту долга.

## Бронирования

- Перед входом получать server decision. Не пускать, если backend вернул запрет
  из-за брони.
- В авторизованном виджете показывать компактную плашку только для будущей
  подтверждённой брони текущего игрового места, принадлежащей вошедшему
  клиенту. Если такой брони нет, блок полностью скрывается.
- Не показывать фиктивные, демонстрационные, гостевые или чужие брони; Avalonia-клиент не
  подставляет значение по умолчанию и не строит бронь из локального состояния.
- За 30 минут до начала любой брони блокировать вход. Для именной брони допуск
  назначенного клиента определяет backend.

## Связь и офлайн

- gRPC heartbeat выполняется не реже чем раз в 10 секунд; portal snapshot после
  входа обновляется отдельным коротким циклом не реже чем раз в 5 секунд. Это
  ограничивает задержку внешнего пополнения баланса без перехода на новый
  realtime-транспорт.
- При потере сети текущая сессия не прерывается. Виджет и клиент продолжают
  работать по последнему серверному снимку.
- Локально сохранять постоянный журнал расхода времени и операций, чтобы после
  reconnect отправить idempotent batch на backend. Нельзя хранить эти факты
  только в RAM или Redis.
- Если на локальном снимке заканчиваются пакет и баланс, завершить сессию и
  заблокировать ПК. Если сеть отсутствует до входа, новую сессию не запускать.
- После последней минуты пакета при невозможности оплатить следующую минуту
  локальный V2 ledger атомарно записывает `SESSION_STOP`, закрывает доступ и
  блокирует application shell; V2 operator command может отдельно подтвердить
  `display.lock`. Активный виджет не остаётся на экране с нулём минут.
- На карте оператора офлайн-ПК остаётся виден с последним клиентом, временем и
  статусом отсутствия связи.

## V2: локальный ledger и Kafka

- Перед новым входом повторное завершение сохранённой остановленной сессии
  использует её тип: гостевая — `StopGuestAccess` с payment ID, аккаунт —
  `StopSession` с client ID. Отказ проверки прав не обходится; локальный журнал
  сохраняется.

- После валидного подписанного snapshot клиент сам выбирает источник времени:
  login grant → активный пакет → подходящий queued package → поминутное
  списание → exhaustion/access-gate. Это единственный поставляемый режим
  клиента; V1 server-backed gRPC-meter и переключатель V1/V2 отсутствуют.
- Локальное хранилище постоянно содержит session state, immutable ledger,
  ClientInbox, ClientOutbox и checkpoint. Изменение времени/денег и запись
  outbox происходят одной локальной транзакцией; память процесса не является
  источником истины.
- Клиент создаёт только заранее разрешённые facts: расход grant/package,
  `PER_MINUTE_DEBIT`, package purchase из локального balance, burn active
  package/grant и session stop. Внешнее пополнение, новый неизвестный клиент и
  новый вход без snapshot при отсутствии сервера не разрешены.
- Outbox worker публикует facts через Kafka с постоянным `operation_id` и
  retry/backoff. ClientInbox дедуплицирует server events до commit offset.
  Heartbeat передаёт состояние устройства и watermarks; он не списывает деньги
  и не подтверждает минуты.
- `BalanceCreditApplied` содержит id пополнения и balance delta. Клиент
  применяет его один раз, не заменяя локальный balance абсолютным server value;
  так pending local debits не теряются.
- До записи `BalanceCreditApplied` сверяется server producer, hash payload и
  точная цель `client_id`/`session_id`/`device_id`. Чужой или повреждённый факт
  не меняет локальный ledger и должен быть возвращён транспортом как controlled
  reject, а не подтверждён как успешно применённый.
- При invalid signature, другом устройстве, sequence gap или clock rollback
  клиент останавливает новые финансовые действия, показывает понятное состояние
  `needs review` и сохраняет journal до server reconciliation.
- Windows V2 host получает только public keyring `GAMECLUB_V2_SNAPSHOT_PUBLIC_KEYS`
  (формат `key_id=base64;...`) из deployment-конфигурации. Отсутствующий или
  повторяющийся key id не допускает запуск V2 host; private signing key никогда
  не передаётся на ПК.
- V2 access-gate вызывает только `OfflineSessionService.Login/Register`,
  создаёт ledger после проверки подписи и ведёт minute timer локально. Он не
  запускает V1 command-loop, который способен создать server-owned session.
- Анонимный гостевой V2-доступ получает только через
  `OfflineSessionService.RedeemGuestAccess`: клиент проверяет отдельную signed
  guest payload, сохраняет guest ledger до открытия access-gate и завершает его
  через `StopGuestAccess`. V1 `session.start/stop` и guest facts для client
  profile в этом потоке не используются.
- При восстановлении гостевого ledger клиент не вызывает кабинет аккаунта.
  Новый вход или регистрация при активном local ledger отклоняются до запроса
  серверного snapshot, чтобы отказ локального хранения не создавал новую сессию.
- До входа Windows V2 host использует только V2 `DeviceControlService`: health,
  enrollment по MAC/`installation_id` и device-authenticated heartbeat. Полученный
  heartbeat содержит policy/тему места, но не V1 session snapshot; локальный ledger
  остаётся единственным источником активной V2-сессии.
- Windows publish собирается через общие `GameClub.Client.Avalonia` и
  `GameClub.Client.Transport.Grpc`; их dependency manifest не содержит старый
  protobuf transport. Linux developer host использует тот же transport и local
  ledger для ручного тестирования; plaintext store остаётся только manual-dev
  boundary и не является production security proof.
- Операторское отключение места — это V2 revocation: следующий heartbeat
  возвращает controlled conflict, Windows немедленно блокирует access-gate и
  прекращает reconnect loop. Durable V2 ledger не удаляется, чтобы факты можно
  было сверить после повторного допуска или вручную разобрать конфликт.
- V2 Windows host подключает только `DeviceControlService` command stream.
  Исполнитель принимает строго `display.lock` и `system.restart`; оба
  сначала блокируют application shell. В нём нет session gateway, поэтому
  operator command не может создать, завершить или meter-ить V1-сессию.

## Enrollment и темы

- Avalonia-клиент запускается автоматически с Windows, сообщает MAC и ждёт назначение
  оператором созданному месту.
- Неизвестный MAC остаётся на заблокированном экране до явной привязки.
- Тема приходит от backend для группы места; фон и визуальный стиль access-gate
  настраиваются темой, а не требуют отдельной сборки.

## Допродажа гостевого времени

- Оператор может добавить любой доступный гостевой блочный тариф в очередь
  активной гостевой сессии, с проверкой зоны, аудитории, канала и окна продажи.
  Оплата прямая; клиентский баланс не используется.
- Платёж допродажи привязан к `session_id`. Подписанный V2-пакет добавляется
  после текущего пакета, один раз на grant; новая сессия не создаётся.
- При выходе или завершении гостевой сессии остаток активного пакета и вся
  очередь сгорают. Допродажу нельзя перенести в следующую сессию.
- V2-клиент передаёт текущую сессию и сохранённые grant IDs при получении
  допродаж. Начальный допуск остаётся schema 1; допродажа использует schema 2
  и не выдаётся клиентам без идентификатора текущей сессии.

## Переносимая папка release

- Поставка Windows x64 — self-contained `release/` с `HubShell.exe`, `server.ini`
  и `start-service.cmd`/`start-service.ps1`. SDK/.NET на игровом ПК не нужны.
- Оператор копирует содержимое в `C:\GameClub` и запускает `start-service.cmd`
  от администратора. Скрипт регистрирует/запускает существующий watchdog на месте,
  защищает весь каталог от записи обычным пользователем и не меняет Windows-аккаунт.
- `server.ini` рядом с EXE содержит `GrpcAddress`, `V2EventsHttpAddress`,
  `V2SnapshotPublicKeys` (только публичные ключи, без токенов/installation id).
  Приоритет: существующие env overrides → INI → assembly metadata/defaults.
  Файл читается один раз при запуске; изменение применяется после перезапуска GUI.
  Адреса проверяются существующей EndpointPolicy; ошибочный файл не игнорируется.
- На каждый ПК переносится чистая папка release, без пользовательского AppData:
  device identity, токены и ledger остаются индивидуальными для установки.

- Ошибка обновления minute ledger закрывает доступ и приостанавливает списания,
  сохраняя локальную сессию для явного завершения; исходное исключение пишется
  в лог. Активный ledger не заменяется новым входом.
