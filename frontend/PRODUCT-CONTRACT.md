# Frontend product contract

## Назначение

Это контракт операторской web-админки. React-интерфейс показывает серверные
данные и отправляет явные команды; он не рассчитывает доступность, деньги,
тарифы или конфликты бронирования самостоятельно.

## MVP-навигация

- Dashboard.
- Карта мест.
- Клиенты.
- Товары и тарифы.
- Аналитика.
- Настройки.

Карта мест обновляет active session и балансированные server statuses коротким
HTTP polling-циклом с целевой задержкой не более 10 секунд. WebSocket не является
обязательным контрактом MVP: переход к realtime допускается отдельным решением.

Текущий dashboard задаёт базовый сценарий MVP: быстрые действия по смене и депозиту,
оперативные показатели, фильтр зон, компактная карта, активность и ближайшие
брони. Не заменять его без отдельного продуктового решения.

## Карта мест — основной рабочий экран

- Карточка места показывает статус, клиента, длительность активной сессии и
  текущий тариф.
- При раскрытии показывать очередь неиспользованных пакетов и доступные действия.
- Из контекста места оператор открывает продажу товара или тарифа, пополнение
  депозита, детали сессии и управление местом.
- При активной именованной сессии контекст места передаёт текущего клиента в
  пополнение депозита и продажу. Получатель не подменяется молча: смена клиента
  требует явного действия и подтверждения, а backend выполняет последнюю
  проверку.
- Сброс пароля в админке только переводит клиента в состояние обязательной
  смены пароля; временный пароль не генерируется и не отображается оператору.
- VNC и удалённое управление экраном не входят в MVP.
- Будущая доработка карты и карточки товара нужна, но их визуальное решение пока
  не задано; не выдумывать новые панели или сущности.
- Все места показываются на одной карте независимо от зоны; зона остаётся
  атрибутом карточки, а позиция — общим one-based номером ячейки.
- Оператор настраивает число столбцов и минимальное число рядов карты.
  По умолчанию — 10 столбцов и 4 ряда; сохранённый выбор оператора
  имеет приоритет. Эта
  визуальная настройка хранится только в `localStorage` текущего браузера;
  карта расширяется, если есть место с позицией за её пределами.

## Продажи и клиентская работа

- Оператор ищет клиента по нику или телефону, пополняет депозит и оформляет
  продажу с явным способом или составом смешанной оплаты.
- Продажа гостю всегда прямая, без депозита и без создания клиента.
- В форме и каталоге продажи backend учитывает аудиторию тарифа:
  `all`, `guest` или `registered`. Тарифы `guest` недоступны при продаже
  зарегистрированному клиенту, а `registered` — гостю. В настройках каталога
  оператор видит и может редактировать все аудитории, но UI не может обходить
  серверное ограничение при продаже.
- Оператор может запускать гостевую сессию: место, гостевой тариф, оплата,
  подтверждение продажи. Только после этого сервер разблокирует место.
- Для V2-места подтверждение гостевой оплаты вызывает отдельную выдачу
  одноразового guest access grant. Frontend не вызывает V1 `/sessions`; ПК
  получает grant через device-authenticated V2 transport и открывает локальный
  ledger только после проверки server signature.
- Клиентские тарифы оператор может оформить и за внешнюю оплату; клиент также
  может сам купить тариф с депозита в Avalonia-клиенте.
- Авторизация клиента на ПК сама по себе не скрывает разрешённые операторские
  способы оплаты. Для активного клиента UI показывает доступные методы и части
  оплаты из server policy; запрещённый backend-метод отображается как ошибка,
  а не как успешная продажа.
- В MVP используются депозит, наличные и перевод. Смешанная оплата состоит
  только из одной наличной и одной переводной части; банковская карта не
  входит в доступные способы оплаты.
- Если на месте есть активный зарегистрированный клиент, переключатель
  `Гость/Пользователь` фиксируется на этом клиенте. UI не предлагает продать ему
  guest-only тариф, а кнопка «Гость» отключена; backend-отказ считается
  обязательной защитной границей.
- Для тарифа с `time_restricted` оператор задаёт отдельно окно продажи и окно
  расходования в минутах локального времени, а также часовой пояс. Вне окна
  продажи тариф не показывается в рабочем каталоге и не принимается backend;
  вне окна расходования купленные минуты не списываются. Frontend отображает
  серверный результат и не рассчитывает доступность по своим часам.
- В подсказке занятого места расчётное «Окончание» строится из снимка сервера,
  но не переносится вперёд из-за запоздалого снимка с тем же остатком. Оно может
  стать позже только после подтверждённого сервером увеличения доступного
  времени: нового пакета, открытия доступного пакета или пополнения баланса.

## Группы клиентов и настройки

- Скидка категории клиента применяется backend к цене V2 при новом входе;
  операторский интерфейс отображает подтверждённый баланс без собственного
  расчёта скидок и списаний. Скидка 100% на поминутную игру не уменьшает баланс.

- В настройках оператор видит и изменяет группы клиентов, флаг разрешённого
  отрицательного баланса и лимит в рублях. UI показывает серверные значения и
  не принимает долг выше backend policy.
- Отдельно выбирается группа по умолчанию для новых зарегистрированных клиентов.
  Изменение этой настройки не переносит существующих клиентов.
- При создании и редактировании карточки зарегистрированного клиента оператор
  выбирает его активную группу. Текущая группа видна в карточке; отключённая
  группа остаётся видимой только у уже назначенного клиента до явной смены.
- Редактор групп клиентов сохраняет `allow_negative_balance` и лимит в integer
  cents; операторский интерфейс не разрешает лимит при выключенной политике.

## Карточка активной сессии

- Hover/focus-card места строится только из server snapshot и показывает
  клиента, баланс, источник и доступное время, названия active/queued пакетов,
  их суммарное время и ориентировочное окончание сессии. Пакет, который ещё
  нельзя расходовать из-за временного окна, остаётся в очереди, но не входит
  в расчёт текущего окончания.
- Если остатка активного временного пакета хватило бы за закрытие его окна,
  карточка ограничивает окончание этим закрытием. Например, пакет на 11 часов,
  начатый в 01:00 при окне до 08:00, показывает окончание в 08:00, а не в 12:00.
- Для зарегистрированной V2-сессии остаток пакета в операторском snapshot
  уменьшается по подтверждённым фактам ledger. Обновление `server_time` не
  возвращает первоначальную длительность пакета и не продлевает окончание
  на прошедшие минуты. Задержка доставки Kafka временно задерживает проекцию.
- Если snapshot устарел, UI явно показывает stale-состояние и время снимка;
  технические UUID вместо имени клиента или места не выводятся.
- Время по разрешённому отрицательному балансу не рассчитывается и не
  показывается: при нулевом или отрицательном балансе UI показывает `0 минут`.
  Решение backend о продолжении поминутной сессии принимается по группе клиента
  и её лимиту долга.

## Уведомления

- Страница настроек позволяет создавать правила порога оставшегося времени:
  включение, звук, системное уведомление и пользовательский текст.
- UI отображает ошибки валидации размера/типа пользовательского звука и не
  считает сохранение успешным до ответа backend.
- Карта и карточка места используют один `session_snapshot`; на MapView и PcGrid
  показывается tooltip с именем клиента, пакетами, server time и stale marker.
  Frontend не создаёт notification event и не считает кредитную формулу.

## Бронирования

- Календарь и карта показывают бронь всегда, независимо от того, именная она
  или гостевая.
- Перед началом брони за 30 минут операторский UI должен отражать, что вход
  заблокирован. Решение и текст причины приходят от backend.
- Гостевая бронь — формальная бронь без клиентской идентификации; именная
  привязана к назначенному клиенту.

## Аналитика

- Нужны личные показатели клиента, показатели зон, каждого игрового места и
  клуба в целом.
- По месту важны игровое время, простой, загрузка за день/месяц и пиковые
  периоды.
- Гостевые факты входят в сводные данные клуба, зон и мест, но не в персональную
  аналитику клиентов.
- Текущая аналитика HubShell остаётся базой; детализация по местам развивается
  отдельным срезом.
- Отчётная группировка по часам, дням недели и когортам выполняется в часовом
  поясе `Europe/Moscow`.
- Подтверждённый платёж считается доходом в момент получения денег. Пополнение
  депозита учитывается как доход один раз, а последующее списание с депозита не
  создаёт второй доход. ARPU, ARPPU и LTV включают игровую и товарную выручку.
- Активность зарегистрированного клиента — игровая сессия или покупка. Гости
  отображаются отдельным показателем гостевых сессий и не входят в клиентские
  retention, churn, LTV, ARPU и ARPPU.
- Возвраты и корректировки доступны оператору как отдельные записи с причиной,
  автором, временем и ссылкой на исходную операцию; исходная продажа не
  переписывается.
- Финансовый аналитический ответ передаёт раздельные значения для полученных
  денег, пополнений депозита, расходования депозита, признанного дохода,
  возвратов и корректировок. `null` означает отсутствие источника, а не ноль.
- Frontend не вычисляет историческую выручку, маржу, retention, LTV или FIFO
  самостоятельно: он показывает значения и состояния, рассчитанные backend.
- Новые финансовые поля добавляются только в versioned/additive read-контракт;
  существующие v1 HTTP/gRPC/CSV consumers сохраняют прежний формат.
- Возле каждого KPI и показателя отображается маленькая info-иконка. Наведение
  или фокус показывает понятное описание, формулу, источник и объяснение
  состояния «нет данных».

## Настройки MVP

- Создание и изменение групп игровых мест.
- Назначение темы Avalonia-клиента для группы.
- Настройка цены поминутной игры в группе игровых мест. Ноль отключает
  поминутное списание для зоны; служебный per-minute snapshot не показывается
  как отдельная позиция для покупки.
- В каталоге и продаже доступны только пакетные тарифы времени; ставка зоны
  применяется backend после login grant и не оформляется отдельной продажей.
- Добавление способов оплаты и изменение порядка отображения.
- Управление группами клиентов, группой по умолчанию и notification rules
  добавляется в существующий раздел настроек без нового универсального
  конфигурационного механизма.

Не добавлять широкую универсальную конфигурацию без отдельного требования.

## V2: операторский статус автономной сессии

- На карте и в панели ПК оператор видит только V2-состояние связи, возраст
  oldest outbox event, последний принятый server sequence и явный
  `needs review`, но не получает из UI право исправить клиентский ledger.
- В поставленном интерфейсе нет выбора V1/V2 и нет переключателя режима
  расчёта. Исторические V1-записи могут отображаться только как read-only
  история из PostgreSQL, без возможности запустить V1-операцию.
- Новые ПК-места создаются только с `v2_local_ledger`. Для V2 места панель не
  вызывает V1 session/meter API и отправляет лишь versioned device-команды
  `system.restart` на
  `/api/workstations/{workstation_id}/device-commands`.
- Кнопка «Заблокировать клиент» временно скрыта: `display.lock` оставляет
  сохранённый V2 ledger активным и может препятствовать повторному входу.
- Для досрочного завершения уже существующей server-owned сессии панель вызывает
  отдельный operator endpoint `POST /api/v1/sessions/{session_id}/interrupt` с
  idempotency key и причиной; это не device-команда и не запускает V1-сессию.
- Backend дублирует эту границу: запрос из старого UI/скрипта не может создать
  V1 session или V1 device-command для V2-места.
- Операторское пополнение остаётся server-side финансовой операцией с
  idempotency key. После успешного server result UI отдельно показывает
  «пополнение принято сервером» и, если ПК offline, «ожидает доставки на ПК».
- Пополнение из панели активного ПК обязательно адресуется именно его
  `session_id` и `device_id`; экран фиксирует получателя, не вызывает V1
  `top-up` и показывает `pending_delivery` как ожидание доставки, а не как
  подтверждение получения Windows-клиентом.
- Dashboard/analytics показывают только подтверждённые сервером domain events.
  Сырые V2 client events, технические ошибки и Loki logs не считаются
  финансовой историей и не подменяют audit.

## Допродажа гостевого времени

- Оператор может добавить любой доступный гостевой блочный тариф в очередь
  активной гостевой сессии, с проверкой зоны, аудитории, канала и окна продажи.
  Оплата прямая; клиентский баланс не используется.
- Платёж допродажи привязан к `session_id`. Подписанный V2-пакет добавляется
  после текущего пакета, один раз на grant; новая сессия не создаётся.
- При выходе или завершении гостевой сессии остаток активного пакета и вся
  очередь сгорают. Допродажу нельзя перенести в следующую сессию.
- V2-клиент передаёт текущую сессию и сохранённые grant IDs при получении
  допродаж. Начальный допуск остаётся schema 1; допродажа использует schema 2
  и не выдаётся клиентам без идентификатора текущей сессии.

- Operator HTTP snapshot гостевой сессии содержит `guest_packages`: текущий
  оплаченный пакет и всю очередь допродаж с snapshot названия/длительности,
  статусом и остатком. Подсказка суммирует эту очередь без повторного добавления
  legacy `active_tariff`. Остаток — серверная оценка по времени начала сессии,
  а не финансовое подтверждение минут локального V2 ledger. Завершённая
  гостевая сессия не возвращает доступную очередь.

## Xbox — согласованный первый этап (2026-10-13, implemented)

- Xbox создаётся отдельным типом места с названием, зоной и позицией на общей
  карте. Для него не нужны MAC, устройство, heartbeat и настройки Windows-клиента.
- Карточка показывает свободное/занятое место, серверный остаток и срок окончания;
  отсутствие клиента не считается потерей связи. При ошибке загрузки статус
  не подменяется локальной догадкой. Время и финансовые правила определяет backend.
- Продажа автоматически гостевая: оператор выбирает Xbox-тариф и способ прямой
  оплаты. Клиента, депозит и поминутный режим выбрать нельзя. Успешная продажа
  сразу запускает сессию; новая продажа добавляет время без второй сессии.
- Форма Xbox-тарифа содержит название, длительность и цену. Тарифы ПК/Xbox
  разделены в выборе и проверяются сервером, включая тарифы без зоны.
- Досрочное завершение требует подтверждения с предупреждением о сгорании
  всего остатка без автоматического возврата. Пауз и переносов нет;
  бронирование будет отдельным этапом. ПК-команды для Xbox не предлагаются.
- Продажи входят в общую финансовую статистику и кассовый учёт; аналитика
  позволяет выбрать Xbox, конкретное место и тариф.
- Без настроенного реле окончание завершает только учёт, TV выключает оператор.
  С DIY-реле ON обязателен до успешной продажи; ошибка показывается оператору.
  При неподтверждённом OFF сессия уже завершена без возврата; карта и панель
  показывают предупреждение о сохранённой необходимости повторного выключения.

Это согласованные требования, а не готовый экран. Реализация:
[план 48](../plans/48-xbox-places/PLAN.md).


## Реле DIY — настройки и ручная проверка (2026-10-13)

- Xbox может иметь необязательные настройки реле: IP в доверенной LAN, порт
  (1–65535) и deviceid. Модель устройства не задаётся; требуется DIY HTTP API.
  Без настроек поведение Xbox прежнее. Обычным ПК реле не назначается.
- Сохранение настроек не переключает устройство. Кнопки «Тест: включить» и
  «Тест: выключить» используют сохранённые настройки; несохранённые поля сначала
  нужно сохранить. Настройки можно удалить, отключив опцию.
- Только оператор с workstations.manage может сохранять настройки и выполнять
  тест. Backend отправляет явный ON/OFF через /zeroconf/switch, затем читает
  /zeroconf/info с интервалом не менее 200 мс. Ошибка протокола, недоступность
  или несовпадение состояния не считаются успешным тестом; результат аудируется.
- Произвольные URL/имена хостов, публичные, loopback, link-local и multicast IP
  не допускаются; HTTP redirects и системный HTTP proxy не используются.
- Автоматические ON/OFF выполняет backend: ON при продаже/старте,
  OFF при stop/истечении. Отказ ON не подтверждает продажу и не запускает
  сессию; отказ OFF не отменяет завершение, а требует повторного выключения.
  Повтор старого OFF не должен выключать новую сессию.
- Подтверждённое состояние реле не является подтверждением картинки на TV.

## Бонусная программа — в работе

Согласованные правила: [план 49](../plans/49-bonus-program/PLAN.md).
Настройки клуба: общий выключатель, начисление за игру (5%), за товары (2%),
предел оплаты игры бонусами (20%, диапазон 0–100%). Оператор может выбрать
оплату пакета бонусами; перед подтверждением показываются серверные цена,
бонусная и денежная части, ожидаемое начисление. Доступный остаток, ожидающие
начисления и резерв показываются раздельно. При долге бонусная оплата недоступна.
Изменения настроек не меняют условия текущей сессии. Гости/Xbox не участвуют.
UI не рассчитывает финансовые правила самостоятельно.

«Изменить бонусы» в карточке клиента открывает точную корректировку: сумма с
точностью 0,01, обязательная причина и подтверждение отрицательной суммы.
Используется отдельный bonus-adjustments API, включая активную V2-игру;
касса и денежный депозит не меняются. Неопределённый ответ сохраняет исходные
данные и ключ для повтора, успех показывается только после ответа сервера.
Из карточки доступна история бонусов с точными дельтами, причиной, автором и
временем. Старое поле целых бонусов в top-up не округляет дроби: для них есть
отдельная корректировка.

Реализованы общие настройки с точностью 0,01%, диапазоном 0–100% и повтором
неподтверждённого сохранения с исходным ключом. В продаже зарегистрированному
клиенту ПК переключатель пакетов изначально выключен; при включении денежная
часть и товары оплачиваются депозитом. Перед каждым пакетом отдельное
подтверждение серверного расчёта, включая 100% бонусную оплату. Количество
пакетов сохраняется; после частичного успеха подтверждённые покупки не повторяются,
при потере ответа используются исходные суммы и ключ. Отмена следующих покупок
не отменяет уже завершённые. Товары бонусами не оплачиваются. В карточке клиента
показаны точные доступные/ожидающие/зарезервированные бонусы; ошибка чтения
не заменяется старой целой проекцией или нулём. Браузерная проверка ещё требуется.


Во вкладке аналитики «Продажи» отдельный бонусный отчёт показывает операции
за выбранный период и текущие остатки на момент загрузки. Область явно указана:
весь клуб, дополнительные фильтры продаж не применяются. Перенос остатков и
ручные корректировки отделены от автоматических зачислений. Суммы показаны
в бонусах отдельно от денежной выручки. Загрузка/ошибка/повтор не подменяются
нулевыми значениями; нули допустимы только из успешного ответа сервера.

### Повторы продажи и контекстное меню карты — 2026-10-19

- Меню места, открытое правой кнопкой, закрывается кликом/касанием снаружи
  или Escape без выбора действия. Нажатие внутри меню само по себе его не закрывает.
- После частичного успеха продажи пакетов подтверждённые покупки не отправляются
  повторно при любой оплате, включая наличные. Неподтверждённый пакет использует
  прежний ключ; смешанная оплата сохраняет исходное распределение частей при
  пропуске уже купленных пакетов.
- Ответ пакета с `pending`/`needs_review` не завершает продажу как успешную:
  оператор видит ожидание подтверждения либо необходимость ручной сверки.
  Автоматического повтора неизвестного денежного результата в браузере нет.

## CI/CD — план 50, реализация не завершена

Замену клиента разрешать только после опроса всех управляемых ПК и проверки
отсутствия активных сеансов на всех ПК. Недоступный/выключенный ПК блокирует
разрешение всему парку. Между финальным опросом и установкой новые сеансы
блокируются общим серверным барьером. При ошибке обновления одного ПК весь
парк остаётся закрытым до устранения ошибки, даже после отката EXE.
Детали и границы реализации: `plans/50-cicd-client-updates/PLAN.md`.

В существующих настройках отображается карточка последней доставки: выпуск,
фаза, число подтверждённых PC и отдельная строка каждой цели с версиями,
состоянием и временем ответа. Состав и числитель назначает backend; недоступный
PC не исключается из знаменателя. Откат отображается как ошибка с сохранением
блока парка. Пустой ответ означает отсутствие доставок, а не успех 0/0.
Карточка опрашивает HTTP BFF, показывает время снимка; ошибка/таймаут скрывает
прежние данные. После закрытия настроек опрос прекращается. Управление выпуском
остаётся в CD/API; карточка читает состояние и позволяет обновить его вручную.
