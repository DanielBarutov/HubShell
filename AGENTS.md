## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

When the user types `/graphify`, use the installed graphify skill or instructions before doing anything else.

Rules:

- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- Dirty graphify-out/ files are expected after hooks or incremental updates; dirty graph files are not a reason to skip graphify. Only skip graphify if the task is about stale or incorrect graph output, or the user explicitly says not to use it.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).

Используй плагин ponytail для всех видов работ, без исключения

## Рабочая среда и ответы

- Вся разработка, запуск приложения и ручная проверка выполняются на Linux-устройстве. Не предполагать наличие Windows-машины для ручных smoke-тестов; для клиента использовать Linux developer/test host.
- Отвечать коротко и сухо: только результат, важные причины и конкретные следующие шаги; без воды и лишних подробностей.

## Основные правила

1. Источники требований

- Перед задачей проверь plans/README.md, plans/SUMMARY.md, относящийся к задаче план и текущее состояние рабочего дерева.
- Перед изменением продуктового поведения сверяй backend/PRODUCT-CONTRACT.md, frontend/PRODUCT-CONTRACT.md и win-client/PRODUCT-CONTRACT.md. Не придумывай отсутствующие бизнес-правила: уточни решение и обнови контракт.
- Подробности функций, текущие статусы и проверки хранятся в plans/<module>/, а не в этом файле. plans/VERIFICATION.md — сведения о проверках; backend/PLAN.md, frontend/PLAN.md, win-client/PLAN.md — общие планы компонентов.
- Если новое решение противоречит требованиям, сначала согласуй и исправь контракт/план, потом код. Не выдавай намерение или описание за готовую реализацию.
- Читай только документы, относящиеся к задаче; не загружай весь plans/ без необходимости.

2. Работа в репозитории

- Все команды выполняй из корня HubShell, без cd в подпроекты: Python — uv run --directory ./backend ..., web — npm --prefix ./frontend ..., Windows-скрипты — ./win-client/scripts/... (PowerShell: .\win-client\scripts\...). В PowerShell пути внутри скриптов строй от $PSScriptRoot.
- Сначала изучи существующий код, интерфейсы и изменения в Git. Не перезаписывай чужую работу и не рефактори соседние модули без задачи.
- Делай небольшие, проверяемые изменения. Не добавляй «на будущее» сервисы, зависимости, уровни абстракции и экраны.
- Изменения поведения сопровождай обновлением соответствующих контрактов, планов, миграций и тестов. Общие protobuf-схемы храни в одном месте.

3. Backend и архитектура

- Backend — модульный монолит. Разделение на микросервисы допустимо только по обоснованной необходимости и отдельному плану.
- Границы модулей обязательны: нельзя обращаться к внутренним таблицам/классам соседей, импортировать их реализацию или передавать ORM-модели через публичные границы. Взаимодействие — через явные порты, DTO, команды и события.
- Соблюдай слои Clean Architecture: Presentation (HTTP/gRPC), Application (сценарии и транзакции), Domain (правила без инфраструктуры), Infrastructure (БД, брокеры, внешние адаптеры). Зависимости направлены внутрь; для портов предпочитай typing.Protocol.
- Бизнес-правила и расчёт цены — в Domain/Application, не в React, SQL или обработчиках транспорта. SOLID/DRY/KISS применяй без лишних фабрик и наследования.
- Асинхронный I/O не должен блокировать event loop; блокирующий код изолируй. Фоновые задачи — Dramatiq с определёнными повторными попытками, таймаутами и идемпотентностью.
- Для денег используй целые копейки, не float. Финансовые операции записывай в журнал с причиной, автором и уникальным ключом; от повторов и гонок защищайся также транзакциями/ограничениями БД.
  Владение данными
- Workstations — ПК, идентичность устройства, зоны, heartbeat, состояние и безопасные команды.
- Clients/Guests — профили, баланс и бонусы, денежный журнал; гостевой профиль не равен клиентскому счёту.
- Catalog — товары/остатки, тарифы, цены, скидки и права на пакетное время.
- Reservations — брони, конфликты, правила входа и серверное EntryDecision.
- Sessions — жизненный цикл фактической игры; не более одной активной сессии на ПК и клиента.
- Billing — единственное списание за сессию, неизменяемый снимок начисления, восстановление после сбоев; баланс принадлежит Clients.
- Cash Shifts — кассовые смены и наличные движения; не изменяет баланс клиента. Интеграции — через plans/09-cash-shifts/PRODUCER-CONTRACT.md.
- Product Sales — завершённые продажи и снимки цен/себестоимости; резерв остатков через Catalog, оплата через владельцев соответствующих счетов.
- Analytics — только чтение подтверждённых исторических фактов (Sessions, Billing, Product Sales), без изменений бизнес-сущностей.
- Для точных состояний, полей, ограничений и новых модулей обращайся к профильному плану и контракту.

4. API и Windows V2

- Protocol Buffers — источник истины для gRPC. Версионируй контракты, сохраняй совместимость, определяй ошибки, таймауты и идентификаторы операций; не передавай секреты.
- Web-интерфейс обращается к backend через согласованный gateway/BFF, а не к PostgreSQL, Redis и внутренним сервисам напрямую.
- Целевой поставляемый Windows-клиент — V2-only. События сессий передаются через Kafka; V1 gRPC runtime, fallback и переключение режимов в поставляемом V2 запрещены. Старый V1-код не считается действующим контрактом.
- Kafka обеспечивает доставку «как минимум один раз»: используй постоянные inbox/outbox, operation_id, порядок и проверку содержимого. Повторные события не должны повторять финансовый эффект.
- Подписанный серверный snapshot может разрешать клиенту локально учитывать известные права/пакеты и сохранять факты для последующего подтверждения сервером. Сервер остаётся владельцем сессии, баланса и окончательного решения; heartbeat не является финансовым подтверждением.
- Изменяющие команды устройству проходят через разрешённый перечень и проверку device identity; произвольные shell-команды из сети запрещены.

5. Безопасность

- Для защищённых действий проверяй JWT (подпись, срок, issuer, audience), идентичность и права на уровне use case, не только в UI/обработчике.
- Храни секреты и ключи только вне Git (окружение/secret storage); не выводи их в логи, ошибки, схемы, web bundle или файлы клиента. Для refresh-токенов используй хеширование, ротацию и отзыв по контракту.
- Записывай автора, время, request/correlation ID и результат изменяющих/денежных операций; рискованные кассовые исправления и закрытие с расхождением требуют отдельного подтверждения и аудита.
- В закрытой доверенной LAN допускается HTTP/insecure gRPC на loopback/private IP по утверждённому контуру; при внешнем доступе обязательны TLS и защищённая точка входа.
- Не смешивай dev fallback с production-гарантиями. Ограничения Windows-окна не равны безопасности операционной системы.

6. Frontend и Windows-клиент

- Frontend: React/Tailwind, иконки Lucide, компактное рабочее место оператора. Главный сценарий — карта ПК и правая контекстная панель; явно обрабатывай loading/empty/error/disabled/success, подтверждай опасные действия, поддерживай клавиатуру. Бизнес-логику оставляй на сервере.
- Windows: только Avalonia, целевая ОС — Windows. До серверной авторизации — полноэкранный Topmost access-gate; после входа — обычный рабочий стол и компактный borderless-виджет с возможностью скрыть его в трей.
- Manager maintenance — отдельная проверка пароля и прав без запуска игровой сессии. Не используй глобальные keyboard hooks (исключение, согласованное пользователем 2026-10-11: Windows hook клавиш Win/Win+D/Win+R только в Locked access-gate, обязательно снимается в User/Maintenance), BlockInput и перехват Ctrl+Alt+Del; app-level lock не заменяет Assigned Access/Shell Launcher.
- Конфигурация и темы приходят с backend; клиент переживает краткий обрыв связи, показывает статус и сохраняет предусмотренные V2 события. Не сохраняй plaintext-пароли и лишние персональные данные.
- Linux пригоден для сборки и части тестов; поведение окон, трей, DPAPI, автозапуск и ограничения обязательно проверяются на реальном Windows-ПК.

7. Качество и проверка

- Python: Ruff для форматирования, проверки и импортов; явные типы публичных методов; внятные доменные ошибки; валидация на границах; UTC/часовой пояс без двусмысленности; структурированные логи без секретов. Комментарии объясняют почему, а не повторяют код.
- Тестируй изменённый уровень: Domain — unit; Application — сценарии; БД/брокеры — integration; API/gRPC — контракты; frontend — сценарии и production build; Windows — сборка, unit и проверка на целевой ОС.
- Базовые команды backend из корня репозитория: uv run --directory ./backend ruff check ., uv run --directory ./backend ruff format --check ., uv run --directory ./backend pytest (проверь фактические команды в README/Makefile).
- Не считай проверку импорта, Linux-сборку или мок-тест подтверждением корректной работы системы, PostgreSQL, браузера либо Windows.
- В конце кратко напиши: что изменено; что реально проверено; что осталось проверить. Для непроверенного укажи где, как и почему текущие проверки этого не доказывают. Пиши простым русским языком, без непояснённого жаргона.

8. Приоритеты
   При конфликте: безопасность и деньги → явное требование пользователя → совместимость контрактов → границы модулей → простота поддержки → удобство реализации. Неоднозначное требование не реализуй как утверждённое правило: зафиксируй вопрос и минимальное безопасное временное решение в плане.
