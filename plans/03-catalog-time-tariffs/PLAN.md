# План 03 — Catalog / Time / Tariffs

Статус: `in_progress`  
Приоритет: `P0`  
Зависимости: `00-foundation`, `01-workstations`, `02-clients-guests`, базовые решения `04-auth-security`

## Цель

Создать единый доменный слой товаров, игрового времени и тарифов, чтобы web, Windows-клиент и будущие сессии использовали один детерминированный расчёт цены.

## Входит в план

- товары и категории;
- игровые услуги/единицы времени;
- тарифы и версии тарифов;
- зона/группа как условие применимости;
- расписания и периоды действия;
- discount category как вход расчёта;
- quote/preview;
- draft, publish и archive.

## Не входит

- фактическое начало/окончание сессии;
- списание баланса;
- внешние платежи;
- складской учёт;
- произвольный код правил из UI.

## Домен и правила

Нужно определить `Product`, `ProductCategory`, `Tariff`, `TariffVersion`, `Schedule`, длительность, цену, currency, rounding и период действия. Опубликованная версия не меняется задним числом. Приоритет тарифов задаётся явно. Денежные расчёты не используют `float`.

Текущий срез добавил расширяемые `DiscountRule` с категорией клиента, периодом действия,
приоритетом и скидкой в basis points. Quote принимает `discount_category`, возвращает
исходную цену, сумму скидки и итоговую цену; расчёт работает только на целых копейках.
Правила доступны через HTTP BFF и gRPC, сохранение и выбор проверены memory и PostgreSQL.
Tariff получает стабильный `tariff_key`, атомарно возрастающий `version` и lifecycle
`draft/published/archived`; публикация и архивирование доступны через HTTP/gRPC, а
published-версии не редактируются application use case-ами. `CatalogSnapshot` отдаёт
клиентам только опубликованные тарифы и активные discount rules одним согласованным
ответом; отдельная аналитическая read model остаётся следующим этапом.
Категории `product`/`drink` доступны через защищённый BFF и выбираются при
создании товара; удаление занятой категории возвращает конфликт до изменения
данных. Товар можно изменить или удалить через operator API; закупочная цена и
остаток валидируются в Domain/Application, отображаются в каталоге и передаются
в gRPC Product/CreateProductRequest. Для обратной совместимости поле `active` в
CreateProductRequest optional, поэтому старые клиенты создают активный товар.
PostgreSQL repository теперь различает создание и обновление товара по его
идентификатору; повторное сохранение существующего товара не вызывает конфликт
primary key.

## Критерии готовности

- тариф выбирается предсказуемо;
- published version не редактируется задним числом;
- одинаковые входы дают одинаковый quote;
- конфликтующие периоды отклоняются;
- archive сохраняет историю;
- rounding проверен на границах;
- draft/publish permissions разделены.

## Риски

- неявный приоритет даст разные цены в разных потребителях;
- изменение опубликованных правил нарушит историю;
- ошибки часового пояса и полуночи исказят quote.
