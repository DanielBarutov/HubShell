# Актуальность серверного состояния V2-сессии

Статус: `planned`, 2026-10-25. Реализация не начата.
Основной план: [PLAN.md](PLAN.md), серверная сверка:
[03-server-reconciliation/PLAN.md](03-server-reconciliation/PLAN.md).

## Результат

Backend применяет доставленные клиентские списания и изменения пакетов,
а оператор получает согласованный баланс, остатки, источник времени и
окончание сессии. Задержка подтверждения явно видна и не маскируется новым
`server_time`. После восстановления связи накопленные факты применяются
однократно, без потери пополнений и без повторного списания.

Это план исправления, не утверждение о причине конкретного инцидента.
Требование актуальности при связи не означает синхронного разрешения каждой
минуты сервером. При отключённом ПК backend не может знать ещё не доставленные
финансовые факты: показывает последнее подтверждённое состояние и его границы.

## Что установлено по исходникам и тестам

- `BillingService` не является вторым счётчиком V2: `meter_sessions_once`
  пропускает `local_ledger`. Это сохранить.
- `/api/events/client-facts` проверяет device identity и публикует protobuf
  в `v2.client-events`; HTTP 202 не означает PostgreSQL commit.
- `V2ClientOutboxPublisher` после успешной публикации вызывает
  `AcknowledgeOutboxAsync`. Проверить сохранность опубликованного факта в
  durable ledger и возможность повторной отправки до серверного подтверждения;
  пустой pending outbox не считать подтверждением финансов.
- Worker `jobs/v2_client_facts_transport.py` уже подключает реальные
  session/entitlement/client writers. Их отсутствие не считать установленным дефектом.
- Reconciliation проверяет lease/snapshot, sequence/hash-chain и дубликаты;
  подтверждённый факт, checkpoint и эффекты пишет транзакционно.
- `V2ClientFactsConsumer` отправляет gap/conflict в `v2.failed-events`.
  Это требует диагностики и контролируемого восстановления, а не пропуска цепочки.
- `SessionService.snapshot` считает минуты баланса из серверного остатка.
  Новые снимки без фактов сохраняют 240 ₽ / 103 минуты. В tooltip
  `frontend/src/features/workstations/sessionTooltip.ts` используется `server_time`;
  точный путь сдвига окончания проверить отдельной регрессией.

## 1. Найти место отставания на одной сессии

- [ ] Сохранить session/device/snapshot IDs, локальный sequence/hash,
  pending и опубликованные факты; на сервере — checkpoint, confirmed facts,
  денежный журнал и остатки пакета. Секреты не выгружать.
- [ ] Проследить один `per_minute_debit`: клиент → HTTP → Kafka partition/offset
  → consumer group `client_session_facts` → результат reconciliation
  → commit Clients → session snapshot → HTTP-ответ оператору.
- [ ] Проверить запущенный `v2-client-facts`, конфигурацию/образ, подключения,
  consumer lag, ошибки, DLQ, lease и snapshot version. Разделить отсутствие
  отправки, отставание consumer, gap, conflict, rollback и устаревшее чтение.
- [ ] Проверить путь active/queued пакета и stop аналогично денежному debit.
- [ ] Зафиксировать первый потерянный/отклонённый sequence и доказанную причину.

Выход этапа: воспроизводящий тест именно найденного разрыва. Если достаточно
исправления запуска worker/конфигурации — выполнить его и проверки ниже,
не переписывая исправную транспортную архитектуру.

## 2. Восстановить подтверждение и накопленные данные

- [ ] Исправить найденный разрыв в существующих publisher/consumer/repository.
- [ ] Различить доставку в Kafka и принятие backend. Проверить существующие
  server result events и checkpoint-reader плана 50; переиспользовать доступные
  механизмы, не вводить второй журнал подтверждений.
- [ ] Для gap найти отсутствующий факт и повторить исходную неизменённую цепочку
  начиная с него. После заполнения gap переобработать более поздние факты из DLQ
  через ту же application boundary, в порядке sequence.
- [ ] Conflict не исправлять подменой snapshot/hash/operation_id или принятием
  произвольного клиентского баланса. Сохранить причину; спорные финансовые
  данные оставить для отдельной сверки с аудитом.
- [ ] При временной ошибке БД не терять сообщение и не подтверждать обработку
  до commit; повтор после сбоя между commit и offset ack идемпотентен.
- [ ] Проверить воспроизведение опубликованных фактов после рестартов и потери
  HTTP-ответа. Если Kafka/DLQ недостаточно и клиент не хранит replayable историю,
  явно выделить минимальное изменение клиента; backend-only этого не исправит.
- [ ] Перед восстановлением конкретной сессии сделать резервную копию затронутых
  данных и отчёт ожидаемых эффектов. Не очищать inbox/outbox/checkpoint и не
  обнулять деньги. Повтор не должен создавать новые финансовые операции.

## 3. Отдать согласованный и честный session snapshot

- [ ] Через публичный read-port Eventing V2 отдать Sessions подтверждённые
  sequence/hash, время исходного факта и время server commit. Прямые обращения
  Sessions к внутренним таблицам Eventing запрещены.
- [ ] Согласовать additive DTO: время формирования ответа отдельно от времени
  подтверждённого состояния, подтверждённый checkpoint и состояние синхронизации.
  Названия и семантику закрепить в backend/frontend контрактах перед кодом.
- [ ] Читать баланс, entitlement и соответствующий checkpoint из согласованного
  DB snapshot: исключить ответ со старым балансом и новым checkpoint при гонке.
  Проверить текущую транзакционную границу и isolation, не предполагать её достаточной.
- [ ] На одной подтверждённой границе вычислять остаток пакетов, денежные минуты,
  источник и прогноз. Сохранять действующий контракт: queued ночной пакет вне
  окна не включается, активное окно ограничивает окончание, долг не даёт
  отображаемых дополнительных минут. Политику тарификации не менять.
- [ ] Проверить кэш session snapshot/карты: новый commit должен быть виден
  следующему чтению; не выдавать старый баланс с новой меткой актуальности.
- [ ] Для оператора минимально адаптировать текущий tooltip: при неизменном
  финансовом checkpoint опорное время прогноза не сдвигается с каждым HTTP
  ответом; показывать время подтверждения и отставание/неизвестную синхронизацию.
  Локальный отсчёт — только прогноз, не изменение серверного баланса.
- [ ] Не считать свежесть heartbeat или отсутствие новых фактов доказательством
  сверки: бесплатная поминутка может не создавать debit. Для точного сравнения
  с клиентом нужен его актуальный sequence/hash; использовать существующий
  путь, а при его отсутствии явно оставить статус неизвестным. Checkpoint из
  heartbeat — диагностический сигнал, не финансовое подтверждение.

Численные пределы задержки и устаревания установить по измеренной частоте
публикации/polling. Не вводить произвольный таймаут как продуктовое правило.
Проверять задержку отдельно: возникновение → публикация → commit → отображение.

## 4. Проверки, необходимые для закрытия

- [ ] PostgreSQL: исходный баланс после покупки 24 000 копеек, ставка 233,
  пакет 660 минут с окном 21:00–07:00 Europe/Moscow, grant=0, старт 19:37.
  Применить факты реального клиентского сценария: 82 debit до 20:59 →
  4 894 копейки; на границе 21:00 package consume без денежного списания.
  Проверить journal, checkpoint, ACTIVE пакет и server snapshot после каждого этапа.
- [ ] В 07:00 применить ordered burn/stop: закрытая сессия, остаток пакета
  сгорел, деньги сохранены. Подтвердить существующие 60 сгоревших минут;
  это текущая семантика границ, не её пересмотр.
- [ ] Повторы, потеря HTTP-ответа, повтор после commit, рестарт consumer,
  временное падение PostgreSQL: один финансовый эффект и непрерывная цепочка.
- [ ] Пропуск sequence, conflict, неверный device/snapshot: запрет частичного
  продвижения; контролируемый replay восстанавливает gap без дублей.
- [ ] Пополнение во время задержки/replay сохраняется поверх корректных debit;
  устаревший клиентский snapshot не перезаписывает баланс Clients.
- [ ] Реальная Kafka + PostgreSQL: остановить consumer, накопить факты,
  показать отставание, вернуть consumer и получить совпадение клиента и сервера.
  Использовать изолированные тестовые session/device IDs.
- [ ] Frontend: несколько ответов с новым `server_time` и тем же финансовым
  checkpoint не продлевают окончание; после нового подтверждения обновляются
  баланс/пакет/время. Проверить tooltip и карточку ПК в браузере.
- [ ] Измерить задержку при исправной связи и восстановление после разрыва;
  зафиксировать результат в VERIFICATION.md. Сборка/unit не заменяют этот прогон.

## Порядок поставки и готовность

1. Диагностика и воспроизводящий тест → минимальный runtime/code fix.
2. Additive metadata и read-model fix → совместимый frontend consumer.
3. PostgreSQL/broker/failure checks → изолированный Linux developer-host прогон.
4. Развёртывание исправленного контура → контролируемый replay накопленного
   → сравнение журнала, checkpoint и операторского снимка одной сессии.

План закрыт, когда подтверждённые факты видны в следующем операторском
обновлении, отставание не выглядит свежими финансовыми данными, replay не
теряет деньги, а реальный сценарий 19:37 → 21:00 → 07:00 подтверждён.
Менять Windows UI, сборку release, цену и число платных границ не требуется;
клиентский transport менять только при доказанном разрыве подтверждения/replay.
