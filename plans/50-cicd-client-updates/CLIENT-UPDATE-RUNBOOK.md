# Независимые обновления ПК: запуск на NAS

Статус: исходники и локальные проверки; на NAS задача ещё не установлена.
План: [INDEPENDENT-UPDATES.md](INDEPENDENT-UPDATES.md).

## Что происходит

CI на main или v-tag собирает GUI/службу/образы и публикует подписанный GitHub
Release. У образов есть `io.hubshell.release-id`; backend также содержит
GAMECLUB_SERVER_RELEASE_ID. Артефакты существующего выпуска не перезаписываются:
повторная публикация того же имени завершается ошибкой, для нового выпуска
нужен новый commit/tag. Feature workflow_dispatch собирает artifact без
публикации GitHub Release. Изменённый workflow ещё не запускался в GitHub.

Сервер разворачивается в Dockhand с digest из подписанного server-release.json.
Серверное обслуживание с несовместимыми миграциями по-прежнему требует отдельного
окна и существующего CD-процесса с backup/restore/migration/readiness.
Новый sync не останавливает контейнеры и не меняет Dockhand/секреты/тома.

Периодическая задача определяет release_id запущенного backend, скачивает
ровно его пакет, сверяет подписи/образы, создаёт локальное зеркало и публикует
policy. GitHub latest не используется: новый клиент не обгоняет сервер.
Backend из нового CI-образа также откажет назначению другого server release,
даже если оно отправлено напрямую через API или на другой адрес backend.

Каждый updater при старте/опросе получает своё задание. Выключенные ПК догоняют
после включения; занятые заканчивают игру. Ошибка удерживает только свой ПК.

## Разовая подготовка после возвращения доступа

1. Опубликовать эту реализацию обычным процессом проекта и получить новый CI
   Release с подписью и label. Старые образы без label намеренно не поддерживаются
   sync: сначала нужен новый server release. Это не обходится выбором latest.
2. Обновить Dockhand stack через актуальный compose.deploy.yml и digest выпуска.
   Применить миграции 0087–0089 по существующей процедуре backup/миграций.
   Настройки текущих рабочих volumes не менять автоматически.
3. Использовать отдельный checkout инструментов на NAS. Нужны Python 3 stdlib,
   OpenSSL и Docker CLI с доступом к проекту `hubshell` и фактическому mount
   release volume. Дополнительный файловый сервис не нужен.
4. Вне Git разместить доверенный RSA public key, тот же, который закреплён у
   updater. Не использовать ключ, скачанный вместе с выпуском, как источник
   доверия. Секрет подписи нужен только CI, на NAS и ПК его нет.
5. Сохранить backend-token.json с access_token/refresh_token оператора,
   имеющего workstations.manage. Права файла 600, каталога 700. Секреты не
   включать в аргументы команд, Git или cron log. Обновление refresh token
   сохраняется существующим JsonApi атомарно.
6. На каждом ПК один раз установить/настроить watchdog через существующий
   installer и enrollment JSON. Служба должна получить backend address,
   machine credential и закреплённый public key; одного GUI EXE недостаточно.
   InstallationId службы и GUI должны совпадать. Watchdog не обновляет сам себя.

## Первый запуск службы на ПК

После регистрации GUI под игровой учётной записью оператор вызывает
`POST /api/v1/client-updates/credentials/<device_id>` с workstations.manage.
Ответ содержит device_id, installation_id и credential_secret; сохранить его
в индивидуальный защищённый JSON, не включать в установочный ZIP. Учётная
запись для первоначального GUI должна совпадать с игровой: идентификатор
установки хранится в её LocalAppData, а служба использует тот же installation_id.

Из C:\GameClub в PowerShell от администратора:

```powershell
.\start-service.ps1 -UpdaterEnrollmentFile C:\Private\pc-enrollment.json `
  -UpdateBackendAddress http://192.168.0.21:8100 `
  -UpdatePublicKeyPath C:\Private\release-public-key.pem
```

Адрес/пути заменить. Обычный двойной щелчок start-service.cmd не передаёт эти
параметры и включает только watchdog recovery. После проверки защищённой
конфигурации убрать временный plaintext enrollment JSON из общедоступных мест.
Первую установку проверить на одном свободном ПК, затем повторить для каждого.
Никакие machine secrets не входят в HubShell.Setup.zip.

## Команда и расписание

Подставить реальные пути существующего пула и backend. Значения ниже — пример,
а не факт наличия каталогов на NAS:

```bash
python3 /mnt/POOL/hubshell/checkout/scripts/sync-client-release.py \
  --public-key /mnt/POOL/hubshell/secrets/release-public-key.pem \
  --job-root /mnt/POOL/hubshell/client-sync \
  --backend http://127.0.0.1:8100 \
  --token-file /mnt/POOL/hubshell/secrets/backend-token.json
```

После успешного ручного запуска добавить эту команду в TrueNAS Cron Jobs
раз в минуту от пользователя с доступом к Docker и mirror volume. На Linux
эквивалентное расписание: `* * * * * <команда выше в одну строку>`.
Cron запускает один короткий проход; свой lock не допускает параллельный запуск.
Задача не ждёт обновления всех ПК и завершается после публикации назначения.

По умолчанию новый вход разрешён только целевому release_id. Если предыдущий
выпуск проверен совместимым с новым сервером, добавить
`--accepted-release-id <previous-release-id>`. Флаг повторяемый, не более 31
дополнительного выпуска. Прозрачного сравнения semver нет. Активные сеансы
продолжаются независимо от списка; новый вход требует свежего GUI-наблюдения.

Параметры cron — источник желаемой policy: не менять её параллельно другим
исполнителем. При незавершённом journal сначала повторить прежнюю команду;
подмена её списка совместимости не допускается. Изменение policy после
подтверждённой публикации создаёт новую операцию.

## Файлы и повтор после сбоя

Mirror volume монтируется backend-http только для чтения. В корне находится
trusted-public-key.pem из операторского источника. Скрипт публикует его
атомарно, не заменяет другой ключ и не следует symlink. Ротация ключа — отдельное
обслуживание. Каждый release_id получает отдельный каталог с release.json,
подписью, ZIP и server manifest. Неполная загрузка не видна как готовый выпуск.

В `<job-root>/<release_id>/assignment.json` сохраняются операция, target/hash,
совместимость и published. Файл записывается до POST. При потере ответа повтор
перечитывает серверную policy и не создаёт дубликат. Exit 0 означает, что policy
опубликована; это не подтверждение обновления всех ПК. Не удалять journal
вслепую. При несовпадении policy/образов/ключа исправить причину и повторить.

HTTP-раздача пакета: `/api/v1/client-updates/releases/<release_id>/HubShell.zip`.
Служба проверяет подпись, размер и SHA-256 независимо от проверок NAS/backend.
Backend не получает write-доступ к mirror и не запускает shell-команды от ПК.

## Восстановление после неудачного выпуска

В существующей карточке настроек оператор нажимает «Повторить с текущей версией»
у failed/rolled_back ПК. Backend повторно проверяет пакет текущей policy и
создаёт новый round того же задания, сохраняя прежний выпуск/хеш/отчёты/GUI
confirmations, автора и время. Барьер ПК остаётся; заново выполняются readiness,
begin-install и двойное подтверждение. Если исправлен сам выпуск, сначала
развернуть соответствующий исправленный server release и дождаться policy sync.

API для автоматизированного повторения:
`POST /api/v1/client-updates/<deployment_id>/retry-current`, JSON
`{"operation_id":"<новый UUID>"}`. При потере ответа повторить тот же UUID.
Для следующей самостоятельной попытки — новый UUID. UI сохраняет ключ в рамках
неудачного round и меняет его при появлении следующего round. Запрос другого
автора с тем же ключом отклоняется. Старый `/retry` сохраняет прежний target
и используется legacy coordinated executor.

## Очная проверка через неделю

- Первый свободный ПК обновляется при выключенном втором; после загрузки второй
  догоняет target. Состояние второго не удерживает первый.
- При активной игре загрузка допустима, замена ждёт завершения. Ledger/outbox и
  server.ini остаются на месте. Новый несовместимый вход запрещён сервером.
- Прервать скачивание, затем повторить; неполный ZIP не устанавливается.
- Проверить сбой запуска, rollback и explicit retry только проблемного ПК.
- Перезагрузить ПК во время замены; проверить восстановление и отсутствие двух GUI.
- Проверить SCM/WTS/DPAPI/ACL, SYSTEM pipe, file locks и реальный запуск GUI.
- Проверить раздачу файлов и запись доверенного ключа через реальный Docker volume,
  обновление токена и повтор cron. Это пока не доказано локальными проверками.
