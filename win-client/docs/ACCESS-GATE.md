# Access-gate и kiosk deployment Windows-клиента

## Что делает приложение

`GameClub.Client` запускается в состоянии `Locked`. В этом состоянии клиент не
показывает баланс, профиль пользователя, игровые действия или административные
данные: защищённый основной контент скрыт до смены режима на `User`. После
успешного входа пользователя приложение переводит сессию в
`User`; после бездействия, потери device-auth или явного выхода состояние снова
становится `Locked`, а после server-side `session.stop` — `SessionLocked` до
повторной аутентификации пользователя.
Потеря фокуса окна сама по себе не блокирует клиент: это обычное поведение
Windows Desktop после входа. Возврат в `Locked` выполняется по idle timeout,
потере device-auth, явному выходу или server-side policy.

Потеря device-auth определяется по `401/403` HTTP либо
`Unauthenticated/PermissionDenied` gRPC на health-проверке; временный offline без
признака отзыва credentials сам по себе не раскрывает и не меняет access-gate.

Режим обслуживания (`Maintenance`) открывается только отдельной проверкой
менеджера. Plaintext-код/пароль не записывается в логи, protobuf, frontend или
обычный конфигурационный файл. Dashboard сохраняет только PBKDF2-verifier для
группы ПК; конкретный device получает его в аутентифицированном heartbeat и
держит только в памяти процесса. Для production дополнительно нужны device
enrollment/rotation и Windows Credential Manager или серверная supervisor-проверка
с короткоживущим разрешением.
В dev без заданного deployment-хеша используется встроенный PBKDF2-хеш значения
`password`; в staging/production явный хеш обязателен. `Ctrl+Alt+P` блокирует
приложение и открывает форму manager access-gate.

## Что приложение не может гарантировать

Обычное WinUI 3 окно не является границей безопасности Windows. `Topmost`,
полноэкранный размер и обработка клавиш не блокируют гарантированно
`Ctrl+Alt+Del`, смену пользователя, диспетчер задач, другой desktop или выход
из процесса. Команда `display.lock` блокирует только GameClub app-shell и не
вызывает `LockWorkStation`: Windows logon и kiosk-ограничения настраиваются
отдельной политикой ОС.

## Production kiosk

Если пользователь должен быть физически ограничен только клиентом игрового ПК,
деплой выполняется через Windows Assigned Access или Shell Launcher:

1. отдельная ограниченная локальная/доменная учётная запись;
2. разрешённый shell — только подписанный GameClub Client;
3. запрет запуска произвольных приложений и выхода из assigned session;
4. локальная политика восстановления клиента после сбоя;
5. менеджерский путь обслуживания через контролируемый Windows admin workflow;
6. ручная проверка обычным пользователем и восстановление после перезапуска.

App-level access-gate и Windows kiosk policy должны включаться совместно, но
остаются разными слоями ответственности.

После подтверждённого `session.stop` клиент планирует перезапуск Windows. Виджет
показывает активную сессию и разрешает самостоятельный выход только после
успешного server-side stop. Для автоматического завершения по недостатку баланса
backend также ставит команды `session.stop` и `display.lock` в очередь устройства;
app callback после подтверждённого `session.stop` применяет policy зоны и при
включённом флаге планирует перезапуск Windows.
`system.restart` остаётся отдельной allowlisted-командой для явных
административных сценариев.
