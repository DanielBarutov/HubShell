## Цель и согласованное условие

Git-выпуск собирает серверные образы и HubShell.zip. TrueNAS с Dockhand
развёртывает сервер, службы на игровых ПК обновляют HubShell.exe, CD получает
сохранённый отчёт по каждому ПК и общий итог.

Согласовано пользователем: замену разрешать только после опроса всех ПК,
если активных игровых сеансов нет ни на одном ПК. Занятый ПК блокирует
всю замену; обновлять свободные ПК отдельно до общего разрешения нельзя.
Принудительно завершать сеансы ради доставки запрещено.

Следующие детали — проектное предложение для реализации, а не готовое поведение.
Согласовано 2026-10-19: недоступный/выключенный ПК блокирует весь парк.
При ошибке обновления одного ПК весь парк ждёт устранения ошибки, в том числе
после успешного локального отката. Таймаут не считается согласием или успехом.
Xbox не получает Windows-клиент и в список опрашиваемых ПК не входит.

## Исходное состояние

- ClientWatchdogService сейчас запускается из того же HubShell.exe через
  --watchdog-service и восстанавливает GUI каждые две секунды.
  Закрытие GUI не освобождает EXE службы для замены.
- Portable-поставка и server.ini уже существуют. Индивидуальные identity,
  токены, ledger и outbox находятся вне обновляемого EXE.
- Корневой Compose использует локальные build; готового .github/workflows нет.
- Автообновление и оркестрация доставки не реализованы.

## Объём и границы

- CI: проверки, сборка один раз, публикация образов по digest и ZIP в Release.
- TrueNAS: локальный исполнитель доставки, локальное зеркало выпусков,
  Dockhand Git stack, миграции и проверки готовности.
- Backend: durable deployment и состояния устройств, общий барьер,
  авторизация службы и отчёты; модульный монолит, без отдельного микросервиса.
- Windows: отдельный стабильный EXE watchdog/updater, установка службы,
  безопасная замена GUI, восстановление и отчёт.
- Frontend: минимальный статус выпуска в существующих настройках;
  первый сквозной этап допускает API/CD-отчёт без нового экрана.
- Не входят: обновление Windows/игр, Wake-on-LAN, произвольные команды,
  принудительная остановка сеансов, автоматический откат БД и самообновление службы.

## Протокол общего разрешения

1. Создать deployment_id, зафиксировать версию и полный список управляемых ПК.
   Новое включение в парк во время доставки требует повторной подготовки;
   недоступные устройства нельзя молча исключать из знаменателя отчёта.
2. Разрешить предварительное скачивание и проверку пакета без закрытия GUI.
3. Выполнить предварительный опрос всех ПК и серверного владельца сессий.
   Если хотя бы один занят/недоступен — ждать, не выдавая разрешение замены.
4. Когда все свободны, установить сохраняемый серверный барьер новых сеансов
   для парка. Закрыть все пути старта: клиент/гость, оператор, grant/recovery
   нового доступа и вход через перенос. Учесть уже выполняющиеся запросы:
   блокировка и создание сессии должны иметь общую транзакционную защиту.
5. Под барьером повторно опросить всех: ответ привязан к deployment_id,
   раунду подготовки и ограниченному сроку свежести. GUI сохраняет локальную
   блокировку входа, сообщает отсутствие активного ledger и состояние pending facts.
   Сервер проверяет отсутствие активных сеансов и незавершённых выдач доступа.
   Несверенные финансовые факты не удалять; до разбора блокировать готовность.
6. Сохранить общее разрешение только при готовности всех ПК текущего раунда.
   Перезапуск GUI/службы, потеря связи или истечение готовности до разрешения
   требуют нового раунда. Повторная команда не создаёт вторую установку.
7. Сначала обновить один пробный ПК, затем остальные — уже под общим разрешением.
   Ошибка пробного ПК останавливает выдачу новых установок остальным.
8. После выдачи разрешения потеря связи означает неизвестный результат,
   а не отмену уже начатой установки. Сверять сохранённое состояние службы.
9. Снять общий барьер после успешного подтверждения всех ПК. При ошибке
   или неизвестном результате хотя бы одного весь парк остаётся закрытым
   до устранения ошибки. Откат EXE не означает успешное обновление. Таймаут
   и рестарт backend не должны самостоятельно открывать вход. Отмена доставки
   с возвратом всего парка на согласованную версию требует отдельного решения.

Готовность устройства и установка связаны с его действующей identity;
одного MAC или обычного heartbeat недостаточно. Нужен ограниченный набор
типизированных действий, без network shell. Служба SYSTEM не должна читать
пользовательский DPAPI-store как будто это её собственный контекст: спроектировать
защищённый локальный IPC с GUI и отдельное ограниченное удостоверение службы.

## Выпуск и установка

Манифест: release_id/version, commit SHA, win-x64, размеры и SHA-256 ZIP/EXE,
подпись, версия формата, диапазон совместимости backend и updater.
Закрытый ключ подписи хранится вне Git/артефактов; публичный ключ закреплён
в службе. Недостаточно скачать ZIP и его хеш из одного непроверенного источника.
Локальное зеркало TrueNAS раздаёт неизменяемые версии по LAN без GitHub-токенов
на игровых ПК. HTTPS и проверка подлинности, защищённые каталоги SYSTEM/admin.

Служба скачивает пакет в staging, проверяет подпись, размеры, хеши и структуру:
только ожидаемый HubShell.exe, без traversal, ссылок и произвольной распаковки.
После общего разрешения приостанавливает watchdog, штатно закрывает GUI,
ожидает завершения процесса, сохраняет старый EXE, заменяет основной,
запускает GUI в пользовательской сессии и ждёт ограниченное время готовности.
При отсутствии пользовательской Windows-сессии не объявляет runtime-успех.

server.ini, identity, токены, ledger/outbox и пользовательские данные не заменяются.
Локальная стадия установки сохраняется до операций с файлами; после сбоя питания
служба восстанавливает определённый старый или новый EXE. Неудачный старт
возвращает предыдущую совместимую версию; откат отражается как ошибка доставки.
Успех требует отчёта службы о хеше установленного файла и независимого
подтверждения backend от запущенного GUI о release_id/device identity.

## Доставка сервера и отчёт

Локальный исполнитель на TrueNAS забирает выпуск исходящим соединением,
без обязательного открытия Dockhand в интернет. Секреты остаются вне Git.
Compose для поставки использует опубликованные образы по digest и постоянные
тома. Не использовать down -v. Один deployment одновременно, уникальные
operation_id для повторов; новые выпуски не вытесняют незавершённый молча.

До перезапуска backend повторно использовать общий барьер и проверку простоя,
если обновление влияет на игровые серверные процессы. Обеспечить совместимость
с предыдущим GUI и службой до окончания всей доставки. Выполнить резервную
копию БД с проверяемым восстановлением, затем миграции отдельным шагом,
развёртывание и readiness/smoke. Только после готовности сервера разрешать
замену GUI; если серверное обновление не удалось — клиентскую доставку не начинать.
Точный порядок миграций и остановки процессов определить для реального состава
Compose; откат образа не считается откатом схемы БД.

Deployment хранит автора, время, версию, список целей, раунд опроса, разрешение,
стадии и ошибки. Отчёт устройства: deployment_id, device_id, старая/целевая/
фактическая версия, стадия, время, код ошибки, результат отката. Отчёты
идемпотентны и не могут перевести состояние назад старым сообщением.
CD опрашивает backend, сохраняет JSON и читаемый итог с числителем/знаменателем.
Успех — только все зафиксированные цели подтвердили нужную версию. Выключенные,
отложенные, ошибочные и откатившиеся устройства перечисляются отдельно.
Таймаут CD завершает job неполным результатом; backend сохраняет доставку.

## Срез 2026-10-19 — постоянный барьер и ядро доставки

Добавлены миграции 0083 (Sessions admission blocks) и 0084 (client update
rounds/reports). Sessions владеет публичным портом block/unblock; запись новой,
повторно активированной или перенесённой сессии проверяет барьер под общим
PostgreSQL advisory lock. Commit переноса использует тот же lock до изменения
владельца. Установка барьера ждёт уже выполняющиеся записи, затем атомарно
проверяет отсутствие активных сессий всех целей. Закрытие парка не основано
на устаревшем HTTP-опросе. Биллинг и данные сессий не переписываются.

Модуль client_updates: доменные состояния polling/preparing/authorized/failed/
completed, новый round_id после подготовки/повтора, свежесть ответов 30 секунд,
контроль identity/sequence/instance и неизменяемого состава целей. Успех требует
хеша службы и отдельного подтверждения GUI; служебная identity не может
подтвердить GUI. Пробный ПК — первый device_id по сортировке; остальные получают
допуск только после его двойного подтверждения. При потере готовности или
перезапуске updater после разрешения — failed, парк не открывается. Явный
operator retry начинает новый раунд с повторной проверкой сервера, не снимая
барьер. Ошибка и даже откат не завершают доставку.

Repository хранит JSONB-снимок с автором/целями/отчётами и уникальный operation_id;
partial unique index запрещает два незавершённых deployment. Изменение состояния
и Sessions barrier участвуют в одной application transaction. Права operator и
ограниченная возможность updater проверяются в application service. Время
приёма отчёта назначает сервер; повтор не продлевает свежесть ответа.

Проверено: 41 тест (новое ядро/real PostgreSQL плюс session/transfer regression),
scoped Ruff check/format. В отдельной пустой PostgreSQL 16 на loopback 55439
успешны upgrade всех миграций, downgrade 0084/0083 и повторный upgrade.
Контейнер hubshell-cicd-postgres оставлен только для следующих проверок этого
плана; рабочие серверы/БД/TrueNAS не менялись.

Это ещё не интегрированный runtime: сервис не включён в bootstrap/HTTP, нет
выдачи/отзыва отдельного удостоверения службы, ограниченного agent polling,
защищённого GUI IPC и новой клиентской логики. Нужно закрыть гонку изменения
парка с финальным разрешением через публичную границу Workstations; одной
проверки списка в service недостаточно. Также остаются signed release/mirror,
CD executor/отчёт, настройка TrueNAS и финальная пересборка EXE/ZIP. Не считать
этап 3 и весь план завершёнными по тестам ядра.

Workstations freeze закрывает гонку финального опроса с регистрацией/архивированием/
сменой MAC или installation, но разрешает heartbeat. Добавление новых PC до freeze
требует нового раунда без исключения исходных целей. Sessions admission закрывает
также повторную выдачу signed access. V2 public readiness сверяет последний sequence/
payload hash локального ledger с confirmed chain; Kafka ingress ACK не равен сверке.

GUI guard запрещает новые user/guest starts, сохраняет активный ledger и не разрешает
закрытие при игре. Machine journal читается до входа; ошибка/неполная запись закрывают
доступ. Windows pipe server проверяет SYSTEM identity; service-side PID/path клиент
ещё предстоит. GUI подтверждает встроенный release_id независимо от службы.
Portable EXE installer делает хешированную копию, журналирует до операций и умеет
восстановить отсутствующий/повреждённый EXE; server.ini/ledger не переписываются.

Проверено: 55 backend tests (включая 9 real HTTP/PostgreSQL), 13 admission/snapshot
checks, 227 .NET tests, Windows GUI/watchdog build на Linux, downgrade/upgrade 0085/86,
scoped Ruff/format, actionlint. Проверки файловой логики на Linux не доказывают Windows
SCM/WTS/file-lock/pipe ACL. Agent loop/config/secure bootstrap, CD runner/mirror/stage,
frontend status, фактическая публикация и финальные EXE/ZIP всё ещё остаются в цели.
Сводка следующего шага хранится в STATUS.md, контракт данных — PROTOCOL.md.

Уточнение этого среза: barrier охватывает также архивные PC, чтобы архивирование
занятого места не обходило правило отсутствия игры на всех PC. Они не добавляются
в список обновляемых устройств, но их активные сессии запрещают начало замены.
Служебный pipe клиент уже проверяет PID/path/session; обязательные IPC поля не
подменяются defaults. GUI оставляет доступным авторизованный maintenance для
исправления ошибки. Подключение клиента к agent loop остаётся следующим шагом.

### Watchdog loop и bootstrap — следующий реализованный срез

Standalone service подключает переносимый HTTP agent и Windows process/pipe adapter.
Агент проверяет подпись/хеши, получает begin-install до закрытия, приостанавливает
watchdog, проверяет локальную готовность ещё раз, заменяет EXE и ждёт healthy GUI.
Потеря installed-report сохраняет здоровый новый EXE для повтора отчёта. Ошибка
восстановления без проверенного EXE не возобновляет обычный watchdog.
Machine config использует DPAPI LocalMachine и закрытый ACL. Installer принимает
индивидуальный enrollment JSON, адрес HTTP backend и закреплённый публичный ключ;
существующая служба должна принадлежать той же папке и LocalSystem.
Packager выпускает отдельный HubShell.Setup.zip с двумя EXE и установщиками.

Проверено на Linux: 236 .NET tests, из них 9 agent scenarios с fake HTTP/process
boundary; обе Windows-сборки без warnings/errors; 5 real ZIP/OpenSSL packager tests;
scoped Ruff/format и git diff --check. PowerShell runtime здесь отсутствует:
SCM/DPAPI/ACL/WTS/file-lock и запуск на Windows этим не доказаны.
CD executor/mirror, frontend status, публикация и финальные EXE/ZIP остаются в цели.

### Подписанный server release, зеркало и части CD

CI до сборки запускает scoped backend tests/миграции на PostgreSQL; после push
подписывает server-release.json с digest трёх образов и общей клиентской версией/commit.
Зеркало скачивает фиксированный GitHub repository, проверяет обе подписи и ZIP,
публикует только целый каталог и не переписывает существующие версии. Compose
подключает mirror volume к HTTP read-only. Полный runner/volume wiring ещё не готов.

Добавлены ядро advancement и JSON/text report всех целей; running_release_id и
первый old_release сохраняются в durable backend payload. Они служат отчёту,
но не заменяют независимое GUI confirmation. Серверный stage останавливает
application writers, проверяет backup обеих БД через pg_restore, применяет
миграции, запускает только приложения и проверяет GetHealth/frontend/API callback.
Отката схемы/снятия барьера на ошибке нет.

Проверено: 56 scoped backend tests на PostgreSQL, 236 .NET tests, 6 mirror,
6 coordinator/report и 4 server-order tests; реальный dump/restore отдельной
тестовой PostgreSQL сохранил контрольную строку и удалил restore DB. Последние
4 теста подменяют subprocess, полный Compose stage ещё не выполнялся. Compose
config validator, scoped Ruff/format/actionlint/diff check прошли. GitHub pipeline,
TrueNAS и Windows по-прежнему не проверены. Следующий шаг: связать части в CLI,
auth/refresh/job/lock/resume, реальный mirror mount и persistent Dockhand images.

### Запускаемый CD CLI

deploy-release.py связывает готовые части: host volume discovery, проверенное
зеркало, clean checkout подписанного commit, durable operation/job, один host lock,
backend auth/refresh, server stage и сохранение digest Git stack в Dockhand.
Автоматический выбор выпуска сначала возобновляет unfinished job; следующий
GitHub latest не может вытеснить его. Timeout/failure сохраняют неполный отчёт;
backend failed требует явного retry. Secret files — private, HTTP — private IP/
loopback либо HTTPS; redirects с bearer не выполняются.

57 scoped backend tests прошли на PostgreSQL. Новый idempotency сценарий сохраняет
исходный список целей при повторе create после добавления PC; новый PC включается
отдельным refresh-targets раундом. 4 real loopback HTTP tests проверяют refresh,
redirect refusal, private files и merge masked Dockhand vars; 8 runner tests с
fake backend/process boundaries проверяют resume/timeout/server failure/selection/
checkout. CLI --help, scoped Ruff/format/actionlint/diff check прошли. Реальный
host invocation/cron, полный Compose pipeline, NAS и Windows пока не проверены.

### Linux .NET / HTTP / PostgreSQL E2E

UpdateAgentHost — test-only консольный процесс с настоящим ClientUpdateAgent;
GUI/process/IPC адаптер симулируется. Два экземпляра по настоящему TCP HTTP
получают updater JWT, скачивают/проверяют RSA ZIP, заменяют реальные файлы;
GUI confirmation отправляется отдельным обычным device JWT.
Сценарий проверяет missing/active PC → prepare запрещён; финальный раунд;
перезапуск отдельного Uvicorn process с другим PID/app/resources/pool и обрыв связи под barrier;
pilot до остального парка; неудачный GUI → проверенный rollback/failed/общий блок;

server.ini и контрольный ledger-файл сохраняются. Это не настоящий V2 GUI ledger
или Kafka transport; их финансовый checkpoint отдельно проверяется backend tests.
