# Sonoff для Xbox: исследование и настройка

Дата проверки: 2026-10-13. Реализованы настройки и ручные тесты DIY;
автоматическое управление сессией и реальное оборудование ещё не проверены.

## Вывод

Для пользовательского MINI-D выбран прямой DIY HTTP: backend → IP:порт реле.
Пользователь подтвердил, что именно MINI-D ранее работал в DIY с Gizmo.
Backend хранит абстрактные IP, порт, deviceid; привязки к модели устройства нет.
Windows-клиент не участвует. Home Assistant/Matter ниже — альтернативный путь,
не зависимость текущей реализации.

**MINI-D нельзя напрямую поставить в разрыв питания телевизора 220 В.**
Производитель указывает выход только для DC-нагрузок и прямо запрещает подключать
AC-нагрузку. Питание самого модуля от 100–240 В AC не означает допустимость такого
напряжения на COM/NO/NC. Выход рассчитан на 24 В DC / 2 А для резистивной нагрузки
либо двигатель 12/24 В DC до 8 Вт.
[Официальная карточка MINI-D, Specs и FAQ](https://sonoff.tech/en-us/products/sonoff-mini-dry-wi-fi-smart-switch-mini-d).

Если TV требуется именно обесточивать, варианты: подходящий силовой коммутатор
либо MINI-D в низковольтной цепи управления отдельного контактора. Схему, защиту,
катушку и допустимость нагрузки выбирает электрик по паспорту оборудования;
катушку 220 В AC нельзя подключать к выходу MINI-D. Производитель предусматривает
работу с контактором.
[SONOFF, применение контактора](https://sonoff.tech/en-us/products/sonoff-mini-dry-wi-fi-smart-switch-mini-d).

Монтаж выполнять при снятом питании; инструкция требует квалифицированного
электрика. Одновременно подавать AC и DC питание на модуль нельзя.
[Руководство MINI-D V1.0, стр. 3–6](https://cdn.shopify.com/s/files/1/0742/9963/8001/files/User_Manual_MINI-D_EN_V1.0.pdf?v=1749029530).

## Уточнение после инструкции Gizmo

Пользователь подтвердил прежнюю работающую настройку через DIY Mode в Gizmo.
[Инструкция Gizmo](https://gizmopowered.helpdeskeddy.com/ru/knowledge_base/art/161/cat/13/nastrojka-umnogo-rele-sonoff)
относится к реле с поддержкой DIY, использует IP:порт и deviceid. Это существенное
подтверждение для того конкретного устройства, пользователь уточнил модель: MINI-D.
Путь через точку ITEAD и страницу `10.10.7.1` соответствует изменённой настройке
DIY v2.0: [README производителя](https://github.com/itead/Sonoff_Devices_DIY_Tools)
различает прошивки 3.3/3.4 (v1.4) и 3.5 (v2.0).

Если используемое реле действительно поддерживает DIY HTTP API, предпочтителен
прямой путь backend → реле по LAN: `/zeroconf/switch` для ON/OFF,
`/zeroconf/info` для проверки, без Home Assistant и Windows bat/exe.
Сначала нужны точная маркировка/прошивка и проверка API на устройстве;
MINI-D по-прежнему не считается проверенной DIY-моделью. Предложение Matter/HA
выше — вариант для MINI-D без подтверждённого DIY API, а не обязательная архитектура.
Поддержка протокола не отменяет ограничения электрической нагрузки.

## Что означает найденный DIY-протокол

Документ пользователя v1.4 датирован 2019-07-31 и ограничен DIY MODE устройств
Basic R3 / RFR3 / Mini с прошивкой от 3.3.0. Он описывает обнаружение
`_ewelink._tcp` через mDNS и HTTP POST `/zeroconf/switch`,
`/zeroconf/info`, `/zeroconf/startup`, `/zeroconf/pulse`.
[ITEAD DIY MODE API v1.4](https://github.com/itead/Sonoff_Devices_DIY_Tools/blob/master/other/SONOFF%20DIY%20MODE%20Protocol%20Doc%20v1.4.md).

Это **не доказательство поддержки MINI-D**. Для MINI-D официально описаны Matter
и eWeLink; публичный прямой HTTP/MQTT API этой модели найденными материалами не
подтверждён. Не переносить инструкции с перемычкой, специальным SSID и прошивкой
старого Mini на MINI-D. Если на руках другая модель, сначала сверить маркировку.
[Руководство MINI-D, способы добавления](https://cdn.shopify.com/s/files/1/0742/9963/8001/files/User_Manual_MINI-D_EN_V1.0.pdf?v=1749029530).

## Сеть и способ установки контроллера

MINI-D использует Wi-Fi 2.4 ГГц и Matter. Для этой Wi-Fi-модели Thread border router
не требуется: это вывод из её транспорта, а не обещание совместимости любой
модели Sonoff.
[Характеристики MINI-D](https://sonoff.tech/en-us/products/sonoff-mini-dry-wi-fi-smart-switch-mini-d).

Matter работает локально через IPv6 и mDNS. IPv6-доступ в интернет не нужен.
Начальную настройку выполняют телефоном через Home Assistant Companion с
Bluetooth; Chrome подходит для панели HA, но не для первичного commissioning.
После успешного подключения управление Matter не требует облака производителя;
полностью офлайн первоначальная установка и обновления здесь не обещаются.
[Home Assistant Matter](https://www.home-assistant.io/integrations/matter/).

Для клуба предлагается **Home Assistant OS в отдельной VM на Linux**, с мостом
в LAN. Официальная инструкция даёт QCOW2 для KVM, минимум 2 ГБ RAM / 2 vCPU,
UEFI и bridged-сеть. Это не переустановка ОС сервера HubShell. При отсутствии
ресурсов/виртуализации можно выделить отдельный поддерживаемый HAOS-узел.
[Установка HAOS на Linux](https://www.home-assistant.io/installation/linux/).

HAOS с приложением Matter Server — поддерживаемый путь. HA Container вместе с
самостоятельным Matter Server возможен, но официальной поддержки этого варианта
нет. В таком случае нужны корректный IPv6 на Linux-хосте, `network_mode: host`
для Matter Server и постоянное хранилище fabric; обычная bridge-сеть Docker
HubShell не заменяет эти требования. Не добавлять контейнеры автоматически в
текущий Compose до выбора схемы эксплуатации.
[Matter Server: Docker и ограничения](https://github.com/matter-js/python-matter-server/blob/main/docs/docker.md).

## Инструкция для первого подключения

1. Сверить MINI-D, прошивку и Matter QR/числовой код; сохранить код вне публичных
   документов. Уточнить модель TV и схему коммутации. Сначала испытывать управление
   реле без подключения сетевого питания TV.
2. Подготовить HAOS по [Linux-инструкции](https://www.home-assistant.io/installation/linux/):
   импорт QCOW2 в KVM/virt-manager, UEFI, LAN bridge, запуск VM и создание учётной
   записи в веб-панели. Закрепить адрес HA через DHCP reservation.
3. Обеспечить общую LAN для HA, телефона и реле; телефон подключить к Wi-Fi
   2.4 ГГц. Убрать client/AP isolation для этого сегмента, разрешить IPv6 multicast
   и mDNS. В HA включить IPv6 Automatic. Изолированные VLAN потребуют отдельной
   проверки маршрутизации и обнаружения.
4. В HA: Settings → Devices & services → Add integration → Matter; установить
   официальный Matter Server. В Companion: Settings → Connectivity → Matter →
   Add device → No, it’s new → сканировать Matter QR и пройти подключение.
   [Шаги 3–4: Matter HA](https://www.home-assistant.io/integrations/matter/).
5. Перед сканированием QR из шага 4 проверить режим подключения MINI-D. При первом включении режим pairing включается автоматически;
   повторный вход — удерживать кнопку около 5 секунд. Индикатор: две короткие и
   одна длинная вспышка; окно подключения 10 минут. Не считать удержание кнопки
   документированным factory reset: инструкция отдельно описывает удаление через
   eWeLink как сброс.
   [Руководство MINI-D, стр. 7–11](https://cdn.shopify.com/s/files/1/0742/9963/8001/files/User_Manual_MINI-D_EN_V1.0.pdf?v=1749029530).
6. В HA найти фактическую сущность реле и назвать, например,
   `switch.xbox_1_tv`. Проверить включение и выключение в панели. Наличие именно
   `switch.*`, набор настроек и отображение состояния MINI-D нужно подтвердить
   на устройстве; имя в примере условное.
7. В профиле HA создать Long-Lived Access Token для служебной учётной записи.
   Хранить токен только в server secret/environment вне Git, не во frontend,
   журнале или настройках места. Не обещать ограничение этого токена одной
   сущностью: разрешённые сущности дополнительно ограничит backend.
   [Авторизация REST API HA](https://developers.home-assistant.io/docs/api/rest/).
8. Проверить API со стороны backend, затем физический TV, восстановление питания,
   отключение интернета при сохранённой LAN, обрыв Wi-Fi и рестарт контроллера.

## Как backend будет обращаться к HA

Предлагаемый протокол: `Authorization: Bearer <secret>` и JSON.
Адрес HA берётся из серверной конфигурации; для места хранится проверенный
`entity_id`, а не произвольный URL.

| Действие | Запрос | Тело |
| --- | --- | --- |
| Включить | `POST /api/services/switch/turn_on` | `{"entity_id":"switch.xbox_1_tv"}` |
| Выключить | `POST /api/services/switch/turn_off` | `{"entity_id":"switch.xbox_1_tv"}` |
| Проверить | `GET /api/states/switch.xbox_1_tv` | — |

Это стандартные endpoints HA. **POST `/api/states/...` меняет представление
состояния в HA, но не управляет физическим устройством**; для коммутации нужен
service call. Ответ HTTP 200 сам по себе не доказывает включённый экран.
[REST API HA](https://developers.home-assistant.io/docs/api/rest/).

Проверка с Linux, **только после проверки проводки и на испытательном выходе**.
Команды ниже ещё не выполнялись. `HA_BASE_URL` заменить фактическим адресом
веб-панели HA, включая используемый порт; не считать `8123` обязательным.
Токен вводится скрыто и передаётся curl через stdin, без ключа в истории и argv.

```bash
HA_BASE_URL='http://<LAN-IP-HA>:<actual-port>'
HA_ENTITY='switch.xbox_1_tv'
read -rsp 'HA token: ' HA_TOKEN
printf '\n'
ha_request() {
  printf 'header = "Authorization: Bearer %s"\n' "$HA_TOKEN" |
    curl --fail --silent --show-error --max-time 10 --config - "$@"
}
ha_request "$HA_BASE_URL/api/states/$HA_ENTITY"
# Следующая команда физически включает выход.
ha_request -X POST -H 'Content-Type: application/json' \
  -d "{\"entity_id\":\"$HA_ENTITY\"}" \
  "$HA_BASE_URL/api/services/switch/turn_on"
ha_request "$HA_BASE_URL/api/states/$HA_ENTITY"
# Выполнить отдельно после наблюдения результата: физически выключает выход.
ha_request -X POST -H 'Content-Type: application/json' \
  -d "{\"entity_id\":\"$HA_ENTITY\"}" \
  "$HA_BASE_URL/api/services/switch/turn_off"
ha_request "$HA_BASE_URL/api/states/$HA_ENTITY"
unset HA_TOKEN
```

Не включать `set -x`, `curl -v` и запись терминала при вводе/использовании ключа.
Пример HTTP предназначен для утверждённой доверенной LAN; при доступе через
недоверенную сеть нужен HTTPS. Проверять из того же сетевого окружения, где
работает backend: `localhost` контейнера не является адресом HA VM.
Панель и API HA не публиковать в интернет; доступ предоставлять только нужным
узлам LAN. Служебную учётную запись по возможности создавать без прав
администратора, проверяя доступность управления на стенде.

Использовать явные `turn_on` / `turn_off`, без `toggle`: повтор доставки команды
не должен переворачивать результат. Полученное `on/off` описывает реле, а не
картинку на экране. `unknown/unavailable` и сетевой timeout показывать оператору
как непроверенный результат, а не успешное выключение.
[Модель switch HA](https://developers.home-assistant.io/docs/core/entity/switch/).

## Предлагаемое поведение HubShell

Это проект интеграции, а не уже согласованный новый продуктовый контракт.

- Для Xbox опция управления выключена по умолчанию. Без неё текущие продажи и
  сессии продолжают работать. Настройка привязывает один управляемый выход к месту.
- Продажа и создание сессии завершаются в PostgreSQL. В этой же транзакции
  сохраняется задание желаемого состояния ON; HTTP-вызов выполняется после commit.
  Ошибка реле не откатывает оплату и не делает повторную продажу. Оператор видит
  предупреждение и может вручную включить TV. Политику потери оплаченного времени
  при неисправности отдельно согласовать перед кодом.
- При продлении обновляется серверный deadline. При завершении желаемое состояние
  OFF. Хранить operation_id, session_id, версию решения, desired/observed state,
  время попытки и ошибку. Автора операторских действий записывать в аудит.
- Исполнитель Dramatiq работает последовательно для одного выхода, с таймаутом
  и ограниченными повторами. Перед **каждой** отправкой и повтором он читает
  актуальную сессию/версию. Старая OFF-задача после продления или новой сессии
  отменяется. Один предварительный check без сериализации недостаточен:
  уже отправленный запоздалый OFF может обогнать ON. Нужны запрет параллельных
  отправок и повторная сверка/коррекция после неопределённого timeout.
- При старте backend и восстановлении HA сверять состояния с текущими сессиями.
  Для активной непросроченной сессии ON, для завершённой OFF. Повтор не меняет
  деньги. Это восстановление желаемого состояния, не гарантия мгновенной доставки.
- Остановка backend/HA/Wi-Fi может оставить TV включённым. Серверный deadline
  сам по себе не отключает физическое реле. Если требуется автономное отключение
  при таких сбоях, отдельно выбрать и проверить локальный watchdog/таймер,
  доступный именно для этой модели и способа интеграции. DIY `/pulse` на MINI-D
  не считать доступным. Не запускать второй независимый таймер без синхронизации
  продлений и защиты от старых команд.

## Что подтвердить на оборудовании до реализации

- Фактическая модель и прошивка, Matter pairing, сущность HA и её доступность.
- TV: автоматический старт после восстановления питания или только standby.
  Замыкание кнопки Power часто означает toggle; такой импульс без отдельного
  подтверждения состояния нельзя безопасно повторять как ON/OFF. Предпочтение
  — устойчивое управление состоянием либо отдельные команды TV с обратной связью.
- Электрическая схема: сухой управляющий вход, контактор или другое силовое реле;
  допустимость нагрузки и защита. XBOX не должен обесточиваться вместе с TV.
- Реакция на внешний переключатель/пульт и power-on state реле после аварии.
  Возможность настройки startup/inching через выбранную Matter-интеграцию не
  подтверждена; наблюдать на конкретном устройстве.
- Требование автономного OFF без backend и допустимое время повторной доставки.

Документы позволяют выбрать протокол и подготовить стенд. Они не доказывают
совместимость конкретной проводки, телевизора или прошивки; приёмка требует
реальных ON/OFF, продления, раннего завершения и сценариев отказа.

## Настройки и ручной тест в HubShell

1. Подключить реле к LAN и включить DIY по ранее использованной инструкции Gizmo.
   IP, порт и deviceid взять из конфигурации устройства/инструмента обнаружения;
   deviceid не заменять MAC-адресом или идентификатором места HubShell.
2. Закрепить IP реле в DHCP роутера. Backend должен иметь доступ к этому IP и порту.
3. Открыть редактирование Xbox, включить «Настроить реле», заполнить IP, порт
   (8081 — начальное значение, фактический порт нужно проверить), deviceid и сохранить.
4. Нажать «Тест: включить», затем «Тест: выключить». Backend отправляет
   `/zeroconf/switch`, через 200 мс читает `/zeroconf/info`; успех означает
   подтверждённое состояние выхода реле, но не подтверждение картинки на TV.
5. После изменения полей сначала сохранить настройки. Снятие опции и сохранение
   удаляет настройки, не отправляя команду устройству.

Используются только локальные IP, без proxy и redirect. Тест требует права
`workstations.manage` и записывается в аудит. Ошибка/timeout не гарантирует,
что выход физически не переключился: проверить его фактическое состояние.
Сохранение, запуск и завершение сессии в этом шаге не переключают реле.
